# 算子内核框架 · 优化文档

> 这份文档回答三个问题：**优化目标到底是什么**、**现在的差距落在哪一项**、
> **下一步该动哪个旋钮**。
>
> 所有数字都是本机上用平台同一条链路实测的，可复算。复算命令见 §2。

---

## 1. 优化目标（先纠正一个常见误解）

**目标不是「越快越好」，是「逐点踩到榜首」。**

平台计分（`scoring.py`）：

```
逐点得分 = points_max × min(1, 全场最优cost ÷ 本队cost)
全场最优 = 所有队伍在该数据点上**做对**的最小 cost
```

- **超过基准不给额外分。** 领先 2 倍和领先 0.1% 是同一个分数。
- **`data/baseline.json` 的 `-O0` 参考解不是计分基准**，只是评测器存的快照。
- 分数随全场变强而下降；并列按最近提交时间排序。

### 1.1 ⚠️ 「达到 -O0 水平」≠「拿到分」

当前开发阶段（内测比赛2）的验收判据是**正确性 + 明显优于 `-O0` 参考解**，
不是名次。这两件事不等价：

| 场景 | -O0 水平的提交拿多少分 |
|---|---|
| 场上还没有更强的提交 | 接近满分（你先提交就设定了基准） |
| 场上有 3× 于 -O0 的提交 | 约 1/3 的分 |

所以本阶段的目标是**把框架打通、把接口留对**；要拿名次，走 §5 的入口清单。

## 2. 代价分解：先量，再改

`cost = 指令数 + 15 × (d_miss + i_miss)` —— 只有三项。**任何优化前先看差距落在哪一项。**

```bash
cd /root/riscv-ai-compiler-platform
set -a && . /root/.riscv_platform_env && set +a
PLATFORM_ENABLE_SANDBOX=0 ./.venv/bin/python \
    /root/workspace/riscv_matmul/measure.py <你的.s> <problem>
```

`measure.py` 逐数据点打印 **instr / d_miss / i_miss / cost / 榜首 / 比值**。
（线上评测器只落库 `d_miss`，所以 `i_miss` 只有本地能看到——排查取指问题时必须来这里看。）

## 4. 三条已确认的结论

### 4.1 指令面已经到顶

`693987 / 64³ = 2.65 条/MAC`，而解析地板是 `2 + (MR+NR)/(MR·NR) = 2.5`
（2 条乘加 + 0.5 条载入）。要再降只能加大 tile ⇒ 需要更多寄存器 ⇒ 不可行。

**结论：matmul 的剩余空间不在指令数。**

### 4.2 N=64 的差距是一次 cache 容量崩塌

`d_miss` 从 N=48 的 **451** 跳到 N=64 的 **3634**（8 倍）。

算一下强制未命中：

| N | 三矩阵字节数 | 缓存行数（64B） | 实测 d_miss | 倍数 |
|---:|---:|---:|---:|---:|
| 48 | 3 × 9,216 = 27KB | 432 | 451 | **1.04×** ← 已达最优 |
| 64 | 3 × 16,384 = 48KB | 768 | 3634 | **4.73×** ← 抖动 |

**N=48 的工作集 27KB < 32KB L1，装得下；N=64 的 48KB > 32KB，装不下。** 这是一个
**容量门槛**，不是连续退化——所以它是个「刀刃还是门槛」问题里典型的**门槛**。

> **N=64 的 54441 差距里，约 42990（79%）是这一项。**
> 另注：**本方案在 N=64 的指令数 693987 ≈ 榜首的整个 cost 694326**——
> 也就是说，未命中清零就基本并驾齐驱。

### 4.3 小 N 的战场是固定开销 + 取指未命中

N=4 时 cost=466，其中指令 256 条、`15×miss = 210`（**占 45%**，其中 `i_miss=9`）。

而 N=4 只算 64 个 MAC（≈176 条指令下限），256 条里约 80 条是固定开销
（平台 wrapper 21 条 + 分发 + 序言）。**小 N 拼的是固定开销的绝对条数。**

## 5. 优化入口清单（按实测收益排序）

| # | 入口 | 现象/机制 | 怎么测 | 框架落点 | 状态 |
|---|---|---|---|---|---|
| **1** | **matmul N=64 的 L1 cache blocking** | §4.2 的容量门槛；可达 gap 的 ~79% | `measure.py` 看 `d_miss` 是否 3634 → ~1000 | `CacheBlocking` | `[P1]` 接口 |

| **3** | **小 N 的固定开销** | §4.3；N=4 单点 466 → 目标 ~440 | 把 256 条拆成 wrapper/分发/序言/主体分别量 | `DispatchLower` | `[P0]` 部分 |
| **4** | **k 循环加「部分展开」档** | 现在只有「全展开」与「真循环」二选一；`i_miss` 在 N≥24 是 29，N=64 因转真循环降到 18 | 扫 unroll ∈ {2,4,8}，看 instr 与 i_miss 的**联合** cost | `LoopFormLower` | `[P1]` 接口 |
| **5** | **per-kernel 起始对齐** | 现在只有段级 `RODATA_PAD`，每个 kernel 的起始地址被动地由前面所有 kernel 的长度决定 | 给每个 kernel 加独立 `.balign` 扫 | `SectionLayout` | `[P1]` 接口 |
| **6** | **`RODATA_PAD` 重扫** | 现值是对 10 个已知 N 扫出来的；**换 wrapper / 工具链 / N 集合都必须重扫** | `padsweep.py` | `SectionLayout` | `[P1]` 接口 |
| **7** | **fp32 的低指令地板**（内测比赛2） | f32 matmul = `fmul.s`+`fadd.s` = **2 条/MAC 且无需 `slli`**；Q16 是 `mulh`+`add`+摊薄的 `slli` | 同 #1 的方法 | `DtypePolicy` | `[P0]` 本阶段 |

**按「是否把某点从 <1.0 推到 ≥1.0」判据**：入口 1 修的是 N=64 单点（差 7.3%，最大单点）；
入口 3+4 修的是其余 9 个点（各差 2~4%，是「面」）。

## 7. 方法论

### 7.1 先量后改

`cost` 只有三项。**每次动手前先跑 `measure.py` 看差距落在 instr 还是 miss**——
这两项的修法完全不同（前者要减指令/加 tile，后者要改访存局部性）。

### 7.2 「刀刃还是门槛」要量不要猜

`d_miss` 在 N=48→64 的跳变是**门槛**（容量 cliff），不是连续退化。门槛型问题的
解法是「让它不越过门槛」（cache blocking 控制工作集），而不是「平滑地调参」。

### 7.3 用已知解回归

任何新 pass / 新模型，**先在已知正确的用例上复现**再谈收益。本框架的回归基线是：
`eval_local.py` 通过 + `measure.py` 的逐点 cost 不退化。

### 7.4 每项工作的判据是「推进了哪个数据点」

因为超基准不加分，**「快了 15%」不是验收标准，「某个点从 0.97 变成 1.00」才是**。
对 matmul 就是：10 个点里 9 个在 0.96~0.98，N=64 在 0.927——**先看哪几个点能被推过 1.0。**

## 8. 反模式（不要做）

| 反模式 | 为什么 |
|---|---|
| 做指令调度 / 周期建模 | 成本口径不含周期，收益恒为 0 |
| 用 `.option rvc` 压缩指令 | 平台 ISA 闸门判**整题 0 分**（`USAGE.md` §2.4） |
| 猜逐点 N 做特化 | 平台自 2026-10-07 起只公布区间；猜不中就全程走通用回退（`USAGE.md` §2.8） |
| 只跑 `measure.py` 就提交 | 它**不跑 ISA 闸门**，测出来的好数字线上可能直接 0 分 |
| 为了让数字好看而改测试 wrapper | 曾经的「数据相关 bug」就是这么来的——错的是脚手架不是内核 |
