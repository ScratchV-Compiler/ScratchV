## 2. 前置条件（D1 上午必须就绪）

### 2.1 工具链

| 工具 | 用途 | 验证命令 |
|---|---|---|
| `riscv64-unknown-elf-gcc` | 编译 RISC-V 目标文件 | `riscv64-unknown-elf-gcc --version` |
| `qemu-riscv64` | 执行验证 | `qemu-riscv64 --version` |
| Python 3.12 + `onnx` | IR 路径依赖 | `python -c "import onnx; print(onnx.__version__)"` |
| `onnxruntime` | 数值基准（ORT） | `python -c "import onnxruntime; print(onnxruntime.__version__)"` |
| `torch` + `transformers` | Qwen3 ONNX 导出 | `python -c "import torch, transformers; print(torch.__version__, transformers.__version__)"` |

### 2.2 ⚠️ 已确认的基础设施阻塞项（D1 必须先解）

截至本文档撰写时，**自托管 runner 上 W1 的 CI 无法运行**，实测证据：

| 阻塞 | 实测现象 | 影响 |
|---|---|---|
| RISC-V 工具链缺失 | runner 上 `clang` / `ld.lld` / `qemu-riscv32` 不全，`sudo` 无免密 → 安装失败 | `probe:qemu-matmul` 无法执行 |
| 到 GitHub 的 HTTPS 不通 | `git ls-remote https://github.com/...` 挂死超时；SSH 正常 | `CI Sync` 步骤失败，任何 job 起不来 |

**处置**：
- 工具链：在有 sudo 权限的机器上执行 `apt-get install --no-install-recommends clang lld qemu-user`（或等价 `qemu-riscv64`），并确认 `qemu-riscv64` 可用
- 网络：见 §7 升级路径

> 这两项**不属于 W1 的技术风险**，是环境问题，但会直接卡住 W1 的 CI 验收。D1 上午必须闭环，否则整周验收无意义。

### 2.3 探测代码的存放约定

```
probes/                      ← 探测代码，不进主分支（或进分支但标记为临时）
  w1_matmul_4x4/             probe:qemu-matmul
  w1_tiny_transformer/       probe:small-transformer
  w1_qwen3_export/           probe:qwen3-onnx
```

探测脚本一律**允许硬编码**、允许只支持单一配置。**不要**为了通用性花时间。

| 时段 | 事项 | 负责 | 产出 |

| 下午 | 同步：确认 ScratchV 现有能力边界（见 [interfaces.md](interfaces.md) §5 缺口表） | E1/E2 | 缺口表复核签字 |

**为什么先做探测 3**：它是四项里最小的，能在半天内暴露"工具链/FFI/数值对比方法"的所有问题。链路先通，后面三项探测才有意义。

**D1 出口**：`qemu-riscv64` 能跑出一个手写/ScratchV 生成的 4×4 MatMul，与 numpy 误差 < 1e-5。

## 7. 升级路径（卡住时怎么办）

| 情况 | 动作 |
|---|---|
| 基础设施阻塞（工具链/网络）D1 中午仍未闭环 | 升级至团队负责人；本周探测改用**本地机器**执行，CI 后补 |
| 探测 2 失败：IR 无法表达 Attention | 立即触发 Plan B（host 端循环 + 静态图），D2 当天上报 |
| 探测 3 失败：后端不产出 FP32 | 触发 Plan B（定点或软浮点），**这会影响全部后续周次**，必须 D1 当天上报 |
| 探测 4 失败：Qwen3 导出不了 | 用手动构造子图替代；同时评估 W2 是否需要调整 |
| 任一探测失败且无 Plan B | 暂停本周，全员讨论是否调整 v1 范围（见计划 §1.3） |
