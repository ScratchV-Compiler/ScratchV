> 上游：[开发计划.md](../开发计划.md) §4.3 W1。负责人：E2 主导，全员参与。
> 状态（2026-10-02）：**本地数值探测已有结果；新路线 CI、团队接口确认与第二人独立复现待验收**。

## 1. 目标和验收边界

W1 要确认 ScratchV 编译 Transformer 的可行性、明确风险和 Plan B、冻结前端/IR/后端/运行时四类接口。出口仍是实际执行的探测门禁、文档定稿及团队确认。文件存在、结构检查通过或跳过后的绿色 CI 都不等于数值验收。

原排期以探测为主，IR 解释器是可复用交付物。现已进一步实现张量 C 后端与 RV64 裸机执行器，这部分属于向 W2/W4 提前推进的实现；不能因此省略 W1 的路线确认、独立复现和风险评审。

当前链路：

```text
ONNX → ONNXParser → shared Program IR → CompilerDriver / 优化 / verifier
     → tensor-c → Zig 0.14.1 / LLVM → RV64GC LP64D ELF
     → qemu-system-riscv64 virt 裸机 → UART 张量输出 → ORT 对照
```

原 `backend=riscv` 标量选择器没有因此补齐张量 MatMul/FP32 能力。旧路径缺口保留在风险 R1–R4；新路线是明确的替代实现，不是旧路径已修复的证据。主计划没有要求必须手写汇编或必须使用 Linux guest；原探测的 RV32 Linux user-mode 配方由上述 RV64 裸机方案替代，须由团队确认。

## 3. 工具链与交付物

| 项目 | 当前约定 |
|---|---|
| Python / 导出依赖 | Python 3.12；CPU PyTorch 2.7.1；其余固定版本见 `requirements/qwen3-small-probe.txt` |
| C 交叉编译器 | Zig 0.14.1，使用 `zig cc`；`SCRATCHV_CC` 指向可执行文件 |
| QEMU | `qemu-system-riscv64`、virt、TCG、RV64GC/LP64D；`SCRATCHV_QEMU` 可指定路径 |
| 本机已测工具 | Zig 0.14.1；QEMU 11.1.0；Windows 便携工具，不需要 WSL |
| Linux 复现 | `qemu-system-misc` 提供执行器；版本写入新报告，不能把 Windows 通过直接当成 Linux 通过 |
| 数学与内存 | Zig 随附 musl 数学库；禁用 fast-math/FMA；静态 arena 默认上限 256 MiB，当前 QEMU 512 MiB |

## 6. 仍未由本次探测覆盖的工作

完整 28 层 IR 累积误差、完整权重装载与内存规划、151936 词表 LM Head 耗时、Tokenizer/生成循环属于后续验收。小尺寸随机权重的成功不能外推这些结论。完整模型静态嵌入或 mmap 的选择尚未冻结；当前裸机环境没有 Linux 文件 mmap 服务。

工具链/网络阻塞时允许“本地先跑、CI 后补”，但 W1 状态保持未关闭。保留失败报告，按 [risks.md](risks.md) 触发方案；不得静默缩短序列、改精度、换模型或降级为 parse-only 后仍标原 gate 通过。

## 7. 2026-10-02 回归收尾记录

本轮在 Windows / Python 3.12 上补齐真实 LLVM 18.1.8 工具后，运行 `pytest tests/`：
**2353 passed，0 failed，40 skipped**。跳过中 38 项需要本机没有的 Linux 用户态
`qemu-riscv32`，另外两个是通用环境未安装 PyTorch 的模块；后者在固定 CPU 环境中
与完整导出入口单测一起执行，**111 passed**。Linux CI 安装用户态与系统态 QEMU，
关键 MatMul 和真实 Qwen3 RISC-V 探测缺工具时必须失败。

独立代码审查随后发现并修复 Softmax 中间减法溢出没有立即报错的问题；追加
Softmax、ReduceMean、MatMul、Mul 溢出和失败后恢复用例，后端/运行时专项
**86 passed、0 skipped**。真实 RV64 ELF 对极端输入返回错误码 2，随后合法输入
得到 `[0.5, 0.5]`。全量计数与之后的专项计数有重叠，不相加宣称总用例数。

对旧提交 `974ee37` 的同环境定点测试实际复现了 Windows 文件占用、路径、换行和
`resource` 导入问题。完整源码归档基线也复现了这些问题；其两个依赖 Git 元数据的
benchmark 在归档目录中不可比较，因此不把这两项失败归因于旧版本。当前工作树的
这两项已通过。缺 `llvm-mca` 的问题通过准备真实工具解决，没有加入整体跳过策略。

任何其他编译错误仍失败。IR verifier benchmark 改为对照优化后的 IR，计时仅代表
验证开关的编译开销，不能与旧版占位汇编计时直接比较。
