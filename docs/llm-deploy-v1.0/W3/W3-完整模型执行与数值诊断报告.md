## 完整七组输入的结果

最终完整证据位于 `output/w3-full-suite-02/`，整套耗时 **222.339 秒**。七组输入均实际执行完整模型：7 个 ORT worker、7 个 IR worker，各执行普通和诊断前向，共 **28 次完整前向**。两个后端的普通/诊断 logits 在各自内部逐元素一致。正式 IR/ORT 比较结果如下，与首轮 `output/w3-full-suite-01/` 相同；普通和诊断 logits 的跨后端误差相同。

| 输入 | 全位置最大绝对误差 | 有效位置最大绝对误差 | padding 最大绝对误差 | `<1e-4` |
|---|---:|---:|---:|---|
| full_seed_0 | 4.67300415e-5 | 4.67300415e-5 | 无 padding | PASS |
| full_seed_42 | 4.86373901e-5 | 4.86373901e-5 | 无 padding | PASS |
| one_token | 4.10079956e-5 | 4.10079956e-5 | 2.81333923e-5 | PASS |

| short_255 | 6.34193420e-5 | 6.34193420e-5 | 2.14576721e-5 | PASS |
| changed_future | 5.14984131e-5 | 5.14984131e-5 | 无 padding | PASS |
| changed_padding | 2.53677368e-4 | 4.10079956e-5 | 2.53677368e-4 | **FAIL** |

因果性和 padding 隔离共四项检查均通过，比较的前缀在两个后端内分别逐元素相同，误差为 0。改变 padding token 后只要求有效 query 的输出不变；正式 IR/ORT 精度比较仍覆盖全部 256 个位置。

七次普通前向的执行时间合计：ORT **27.811 秒**，IR **42.794 秒**。整套 222.339 秒还包含诊断前向、解析、模型/源码哈希、进程启动、写盘和产物复核，不能当作单次推理耗时。这些是本机 CPU 上的 ORT/NumPy IR 测量，完整 28 层尚未在 RISC-V/QEMU 执行。

中间检查点的 `1e-4` 标记用于定位，正式门槛适用于完整 logits。第 2 层一些 residual 值约为 6872，单个 FP32 ULP 约 `4.88e-4`；中间值绝对误差超过 `1e-4` 本身不能证明矩阵乘或解析语义有错，也不能用于取消 logits 的正式门槛。

## 数值差异定位

short_17 的 embedding 完全一致，第 0 层 residual 已出现约 `6.97e-6` 的差异，随后逐层传播。其最终最大 logits 差异位于 query 80、token 126661，属于 padding query。final norm 最大差异约 `5.36e-4`。

使用完全相同的局部输入，实际运行原 ONNX 算子经 parser/IR 的结果与 ORT 比较：

| 第 0 层局部操作 | IR/ORT 最大绝对误差 | 解释 |
|---|---:|---|
| input RMSNorm 的 ReduceMean | 2.32830644e-10 | Pow 输出相同后首次出现舍入差异，此时尚未进入 Attention/mask |
| Q 投影 MatMul | 3.81469727e-6 | 存在 FP32 数值差异，未发现形状或转置语义错误 |
| K 投影 MatMul | 1.66893005e-6 | 同上 |
| Attention QK MatMul | 0 | 当前相同输入下逐元素一致 |
| Attention Softmax | 1.78813934e-7 | 双方所有屏蔽概率严格为 0 |

独立 FP64 局部诊断中，ReduceMean 的 IR 误差约 `8.00e-11`，ORT 约 `2.59e-10`；IR 在这个位置反而更接近高精度参考。Q/K 投影的 ORT 局部误差较小。证据支持多种 FP32 归约和矩阵乘舍入差异叠加的解释，尚未证明所有最终误差只来自某一个算子。不能仅为贴近 ORT 而硬编码某一输入的累加顺序。

可复用的 [局部诊断入口](../../../probes/w3_qwen3_full/LOCALIZE.md) 已实际运行，证据为 `output/w3-full-localize-01/report.json`：读取首轮 short_17 的固定证据，检查第 0/21 层及五个原语，耗时 **5.258 秒**，进程峰值 RSS **888,676,352 字节**。同输入下这两层的 residual 最大差异分别约 `6.97e-6`、`6.10e-5`。报告的 `COMPLETE` 只表示诊断完成，`numeric_gate_passed=false`；它不替代完整七组验收。

历史 short5 的 Torch/ORT padding 差异也已独立复现：逐层官方 Torch 加同一分块 head 与旧完整 Torch logits 全部逐元素相同；ORT 层状态经过该共享 head 与 Torch 相差约 `0.00216293`，接近历史 `0.00216198`。这条实验与本轮正式 IR/ORT gate 分开保存；它不代替正式参考或验收结果。实验脚本、逐层数组和说明位于 `output/w3-padding-diagnosis/`。

## 内存对照与测量边界

在相同 short_17 输入上，默认 parser 加复制/保留全部中间值的解释器实际峰值 RSS 为 **10,341,670,912 字节，约 9.63 GiB**。本轮新模式的完整 worker 实测约 **2.80 GiB**，其普通和诊断执行都保留完整 logits。默认策略输出与新策略 logits **逐元素完全一致**，支持内存策略没有改变本输入数值结果。对照证据为 `output/w3-full-default-memory-01/report.json`。

解释器默认策略的去重 buffer 峰值为 `5,451,086,568` 字节；新模式约 `2,397,770,952` 字节。该计数包括当时已绑定的借用数组，不包括已解除绑定却仍由调用方保留的对象、内核临时缓冲或观察器拷贝。Windows mmap 的对齐前缀及独立映射也会计入 buffer 估算。它不等同实际 RSS。

内存对照同时发现并修复了首版监控缺陷：Windows venv Python 的 `Popen.pid` 是启动器，实际计算发生在另一个进程，旧父监控只看到约 6 MiB，未执行到原定 8 GiB 的终止条件。因此 `w3-full-suite-01` 和 `w3-full-default-memory-monitor-01.json` 的父进程采样不能作资源限制有效性的证据；实际 worker 的自测 RSS、张量和数值比较不受该采样问题影响。

修复后先挂起创建 Windows 启动器，将其加入本次拥有的 Job Object，再恢复运行；内存采样和终止均覆盖整个 Job。实际 venv 启动器加计算子进程的回归测试，在 96 MiB 上限下采样到 RSS `145,768,448` 字节、私有提交 `134,787,072` 字节，正确触发超限终止，并通过持有的实际子进程句柄确认子进程退出。超时、中断、启动器先退出但后代仍运行也有回归覆盖，证据为 `output/w3-job-tree-01.xml`。

最终 suite02 的 14 个 worker 均记录 `ownership=windows_job`，每次实际采样到至少两个进程，没有清理错误；运行上限为 10 GiB。ORT/IR 的 worker 自测峰值 RSS 分别为 **4,247,453,696 / 3,003,027,456 字节**（约 **3.96 / 2.80 GiB**）；父监控采样的进程树 RSS 峰值分别为 `4,243,689,472 / 2,962,190,336` 字节。采样可能错过短峰值，进程树共享页也可能重复计数，两个口径不能混用；该措施不是操作系统硬内存配额。

同一进程树管理也接入五项准备检查的总入口，修复 Windows venv 后代在超时或中断后可能残留的问题。准备入口只记录内存并限制耗时，没有声称为这五项配置实际内存额度。

复现命令、完整输出及耗时字段见 [完整模型入口](../../../probes/w3_qwen3_full/README.md)。完整执行成功与精度通过是两件分别记录的事实；统一报告的 `full_ir_executed=true` 不会自动令 `passed=true` 或 `w3_exit_accepted=true`。
