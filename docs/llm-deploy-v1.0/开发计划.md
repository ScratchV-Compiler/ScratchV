# ScratchV 上部署 Qwen3-0.6B 设计方案

**版本**：v1.0  
**范围**：FP32 + 固定序列长度 L=256 + 无 KV Cache + 无 INT8  
**目标平台**：RISC-V（QEMU 验证，真实硬件可选）  
**团队规模**：5 人初级工程师  
**周期**：8 周  
**验收方式**：CI 门禁驱动

---

## 1. 项目概述

### 1.1 背景

ScratchV 是一个面向计算机体系结构与编译原理学习的 AI 编译器，核心管线为 ONNX 解析 → IR 构建 → 优化 Pass → RISC-V 代码生成。当前主要验证于 CNN 类静态计算图。本项目旨在**尽可能沿用 ScratchV 框架**，通过扩展前端、IR、后端和运行时，使其能够编译并执行 Qwen3-0.6B 的 Transformer 前向传播。

### 1.2 目标

在 RISC-V 平台（QEMU）上运行 ScratchV 编译的 Qwen3-0.6B，对简单 prompt 生成连贯文本。

### 1.3 v1 范围界定

| 维度 | v1 决策 | 理由 |
|---|---|---|
| 数据类型 | FP32 | 避免量化节点解析、定点运算、量化误差对齐 |
| 序列长度 | 固定 L=256 | 避免动态形状支持，所有张量形状编译时确定 |
| KV Cache | 不支持 | 避免动态内存、循环结构、缓存管理 |
| 推理模式 | 单次前向 + host 端 token 循环 | ScratchV 生成直线代码，循环在 host 端 |
| 采样 | Greedy 优先，top-k/top-p 可选 | 先验证正确性，再丰富策略 |
| 目标平台 | QEMU riscv64 | 功能验证，性能数据参考 |

### 1.4 排除项（后续版本）

- KV Cache（v2）
- INT8/FP16 量化（v2/v3）
- RVV 向量扩展（v3）
- 真实 RISC-V 硬件性能调优（v3）
- 动态序列长度（v2）
- 多 batch 推理（暂不需要）

## 2. 技术架构设计

### 2.1 整体数据流

```
┌─────────────────────────────────────────────────────────────────┐
│                         Host 运行时                              │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐     │
│  │ Tokenizer│──▶│ 掩码构造 │──▶│ FFI 调用 │──▶│  采样    │     │
│  └──────────┘   └──────────┘   └────┬─────┘   └────┬─────┘     │
│                                      │              │           │
│                                      ▼              ▼           │
│                              ┌──────────────────────────┐       │
│                              │   Token 循环 + 历史更新   │       │
│                              └──────────────────────────┘       │
└──────────────────────────────────────┬──────────────────────────┘
                                       │ FFI
                                       ▼
┌─────────────────────────────────────────────────────────────────┐
│                    ScratchV 编译产物（RISC-V）                    │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐     │
│  │Embedding │──▶│ 28 层    │──▶│  LM Head │──▶│  Logits  │     │
│  │  Gather  │   │Transformer│   │  MatMul  │   │ [1,256,  │     │
│  └──────────┘   └──────────┘   └──────────┘   │ 151936]  │     │
│                                                 └──────────┘     │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 ScratchV 编译管线扩展点

| 阶段 | 现有能力 | 需扩展 | 负责模块 |
|---|---|---|---|
| 前端 | ONNX 解析（CNN 算子） | RMSNorm、RoPE、SwiGLU、GQA 模式识别 | `frontend/` |
| IR | SSA 三地址码 | Attention 节点、RoPE 节点、SwiGLU 节点 | `ir/` |
| 优化 | 5 个 Pass | fused attention（可选） | `optimizer/` |
| 后端 | RISC-V 代码生成 | FP32 MatMul、Softmax、RMSNorm、Attention | `backend/` |
| 运行时 | 无 | Tokenizer、采样、掩码、token 循环 | 新增 `runtime/` |

### 2.3 Qwen3-0.6B 关键配置

| 参数 | 值 |
|---|---|
| 层数 | 28 |
| hidden_size | 1024 |
| intermediate_size | 3072 |
| Q 注意力头数 | 16 |
| KV 注意力头数 | 8（GQA） |
| head_dim | 128 |
| vocab_size | 151936 |
| 位置编码 | RoPE（partial） |
| 激活函数 | SwiGLU |
| 归一化 | RMSNorm |
| 权重绑定 | 是（Embedding 与 LM Head 共享） |

### 2.4 固定长度推理模式

```
输入：
  input_ids:      [1, 256]        int64
  attention_mask: [1, 1, 256, 256] float32

输出：
  logits:         [1, 256, 151936] float32

Host 端循环：
  1. 编码 prompt → input_ids
  2. 构造 attention_mask（因果 + 填充）
  3. 调用 RISC-V 前向函数
  4. 取最后一个位置的 logits
  5. 采样下一个 token
  6. 追加到 input_ids，重复 2–5
  7. 直到 EOS 或 max_length
```

**关键约束**：每次前向都处理完整的 256 长度序列，不足部分用 pad token 填充。这避免了动态形状，代价是 `O(N²)` 计算量。

## 5. 风险与应对

| 风险 | 概率 | 影响 | 缓解措施 | Plan B |
|---|---|---|---|---|
| IR 无法表达注意力 | 低 | 高 | W1 探测 2 提前发现 | 改用 host 端循环 + 静态图 |

| 数值误差累积 | 中 | 高 | 三层验证（小/中/完整） | 逐层对比，定位误差源 |
| 后端不支持 FP32 | 低 | 高 | W1 探测 3 提前发现 | 改用定点或软浮点 |
| QEMU 内存不足 | 中 | 中 | W1 提前测试 | `-m 8G` + mmap 权重 |
| 初级工程师卡住 | 高 | 中 | 结对编程 + 外部导师每周 review | E2+E5 结对，导师介入 |
| 接口不统一 | 中 | 高 | W1 冻结接口 + 每日站会 | PR review + 集成日 |
| 集成冲突 | 中 | 中 | 每周集成日 + 小步提交 | 提前合并，分支保护 |

v1 完成后，按优先级推进：

| 版本 | 功能 | 预期收益 | 预计周期 |

## 8. 总结

本设计方案的核心逻辑是：

1. **范围最小化**：FP32 + 固定长度 + 无 KV Cache + 无 INT8，让 ScratchV 回归其最擅长的静态计算图编译。
2. **风险前置**：W1 整周预研，用 5 天换取对整个项目可行性的判断。
3. **三层数值验证**：小模型 → 中等模型 → 完整模型，每层独立门槛，避免最后才发现问题。
4. **CI 门禁驱动**：PR 快速门禁、Nightly 完整门禁、Weekly/Release 门禁，四个硬门槛自动判定。
5. **周粒度管理**：降低管理开销，每周集成日，W8 纯缓冲吸收延期。
