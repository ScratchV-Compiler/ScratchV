# ScratchV 架构设计 —— 面向 LLVM 的兼容与超越

> **与 `ARCHITECTURE.md` 的关系**：那份描述**现状**（ONNX→RISC-V 全流程、模块地图、
> 数据流）；这份描述**设计**——为了「兼容且超越 LLVM」，ScratchV 的每一层该长成什么形状。
> **本文件不改动 `ARCHITECTURE.md`**，对它的矛盾条款只在附录 C 逐条标注。
>
> **本阶段原则**：**只预留接口，不实现。** 每一条现在的最小动作都保证**行为不变**。
>
> **本版删掉了上一版自造的全部代号**（原来叫 `X1–X4`、`S1–S8`、`兼容面`、`缝`、
> `边界借用`）。现在每一处引用都用**它自己的名字**，第一次出现时就地说明。

---

## 1. 兼容：每一层都能换上 LLVM 的对应物

「兼容 LLVM」不是"能产出 LLVM 的输入输出"，而是**逐层的形状同构**：
在任何一个层边界上，把 LLVM 的组件换进来，链路仍然成立。

| 层 | LLVM 的对应物 | ScratchV 现状 | 目标形态 | 能换吗 |
|---|---|---|---|---|
| 前端 | clang / torch-mlir | `frontend/`（ONNX parser、DSL parser） | 统一的前端接口 | 可换 |
| **IR** | LLVM IR（SSA / 带类型 / 内存模型） | `scratchv/ir/` | **语义对齐 LLVM IR 的一个子集**（§3） | **可映射** |
| 分析 | AnalysisManager | `scratchv/analysis/` | 同形状 | 可换 |
| 中端优化 | PassBuilder + 200+ 个 pass | `scratchv/optimizer/`（5 个） | 注册表驱动 | 可换 |
| **成本模型** | TTI（虚函数，4 个固定 `cost-kind`） | `cycle_estimator.py` + 内核层常量 | **成本模型可替换、可作搜索目标** | ★ 见 §2 |
| 指令选择 | TableGen + ISel | `instruction_select.py` / 内核 | 可插拔 | 可换 |
| 寄存器分配 | Greedy / Basic | `register_alloc.py` / `regalloc_linear.py` | 同形状 | 可换 |
| 汇编发射 | MC layer | `asm_emit.py`（GAS 语法） | 同形状 | 可换 |
| **目标描述** | TableGen → C++（**编译期固化**） | **散在 15 个文件**（§5） | **运行时可加载** | ★ 见 §2 |
| **形状 / 值域** | IR 类型系统里**没有这个位置** | 形状有位置但不被后端接受；**值域完全没有**（§3.1） | **进 IR 类型系统** | ★ 见 §2 |
| **特化内核** | 无 | `kernels/`（**外挂**，主线零调用） | **后端可调用** | ★ 见 §2 |

**兼容 = 其余每一层可换；超越 = 右列那四处。**

### 1.1 「可换」的判据是结构性的，不比快慢

| 层 | 怎么算换得动 |
|---|---|
| IR | 存在 `ScratchV IR → LLVM IR` 的映射，且语义保持（两个解释器对拍） |
| 中端优化 | pass 只依赖 IR 和成本模型，不依赖具体前端 |
| 后端 | 加一条后端不需要改 `compiler.py` 的分派逻辑（现状：4 条路径硬编码在这里） |
| 目标描述 | 改一处，全仓库行为一致地跟着变 |
| 内核 | 主线能把内核当组件调用；不调用时产物逐字节不变 |

## 2. 超越：LLVM 做不到的四件事

「超越 LLVM」不是一句总目标，它只有四个具体来源——只有在这些地方，
LLVM 的架构是**做不到**，而不是"做得不够好"。

| LLVM 做不到的 | 为什么做不到 | 做到之后能赢什么 |
|---|---|---|
| **目标描述运行时可加载** | TableGen 在**构建时**把 target 固化成 C++；换 target 要重新构建 | 加一个 target = 加一份数据 |
| **成本模型可替换、可作搜索目标** | TTI 是 pass 内部的**局部查询**，可切集合固定为 4 个 `cost-kind`（附录 B.2 实测） | 换个目标函数就换一套最优解 |
| **形状和值域进 IR 类型系统** | LLVM IR 的类型系统里**没有形状**（张量早被降成内存） | 全图特化、按值域做代数重写 |
| **内核可被后端调用** | LLVM 不会有"这个形状的手工内核" | 手工内核的收益能回流到编译链 |

### 2.1 追不上的地方不要追

**寄存器分配、一般循环优化、指令选择的一般情况**——LLVM 有二十年积累，追不上，
也不在上面那四条里。架构上**只给它们留可换的位置**（§1 的表），不需要做得更好。

## 3. 一个不可逆的决定，和它的两条后果

其余一切都可以晚做（pass 怎么实现、成本公式怎么写、怎么测——全部可逆）。
只有下面这一件事**现在不定，以后改不动**。

> 上一版把这里写成了「三个不可逆的决定」。那是错的——**真正的决定只有一条**，
> 另外两条是从它推出来的后果，不需要单独拍板。

### 3.1 决定：形状是不是 IR 的正式信息

| 选项 | 做法 | 能表形状吗 | 代价 |
|---|---|---|---|
| **A** | **自己定义 IR**（现状）：算子、类型都由 ScratchV 自己定 | ✅ 能（自己的类型系统） | 要和 LLVM IR 互通得**自己写转换**；现在只有单向（`llvm_codegen.py`） |
| **B** | **直接用 LLVM IR**，不自己定义 | ❌ **不能**——LLVM 类型系统没有形状，张量只能降成「内存 + 指针算术」 | 转换免费 |
| **C** | **改用 MLIR**，用它的类型系统 | ✅ 原生（`tensor<2x2xf32>`） | 迁到 MLIR 生态，成本高 |

**推荐：A 的做法 + C 的存储方式。**

- **用 A**——保住自己的 IR，因为你要放 LLVM 确实没有的东西（形状）；
- **借 C 的做法**——把形状和值域放进 **IR 的类型系统**，而不是塞进 `attrs` 这类地方。

**不全选 C（改用 MLIR）的理由**：迁移是大工程，而当前需要的兼容只在**后端那一层**（§3.2）。

#### 这句推荐为什么容易看不懂

A / B / C 表面是「三选一」，实际是**两个独立的决定**缠在一起：

| 独立的决定 | **A** | **B** | **C** |
|---|---|---|---|
| **① 谁定义 IR 的词汇**（有哪些算子、类型怎么表示） | 自己定 | 用现成的 LLVM IR | **在 MLIR 框架上自己定义方言** |
| **② 形状这类信息放哪儿** | 塞在旁边（现在塞 `attrs`） | **没地方放**（于是退化成 `fmul`） | 放进**类型系统**里 |

**注意 A 和 C 在 ① 上是同一路人**——都是"自定义 IR"，C 只是借了 MLIR 的框架来定义。
它们真正不同的只有 ②。

所以「A 的做法 + C 的存储方式」**不是两个选项相加**，它的意思是：

> **走 A 这条路（自己定义 IR，不搬进 MLIR 生态），但把 ② 那一格换成 C 的做法。**

拿掉口号就是一句：**「自己定义 IR，但形状归类型系统管。」**
现状则是：自己定义 IR（①=A）+ 形状塞在 `attrs` 里（②≠C）。

#### 现状核对（写本节时实际查到的）

| | 实际状态 |
|---|---|
| **形状** | **位置已存在**：`ir/types.py:112` 的 `Value.shape: tuple[int, ...] = ()`；而且**已被使用**——`verification/ir_interpreter.py` 拿它做形状校验，`optimizer/hoist_safety.py:214` 读它 |
| **形状的缺口** | riscv / llvm 后端遇到非空形状**直接拒绝**：`compiler.py:527` `cannot lower tensor buffers` |
| **值域** | **完全没有表示**（全仓库找不到 value-range / interval 类型） |

**同一个概念在 ScratchV 里有两套存法**，这才是真正的问题：

| 来源 | 形状存在哪 | 结果 |
|---|---|---|
| ONNX 模型（`cnn.onnx`） | `Value.shape` 字段 | 撞上闸门 → 明确报错 |
| DSL（`matmul(A,B,m:2,n:2,k:2)`） | 指令的 `attrs` 字典（打印出来是 `[m=2]`） | **闸门认不出** → 一路放行到 LLVM → 悄悄变成 `fmul` |

实测对照：

```
$ matmul(A,B,m:2,n:2,k:2) --backend ir     →  $v_1 = matmul $A $B [m=2] [n=2] [k=2]
$ 同一个程序  --backend llvm               →  %v_1_1 = fmul float %A, %B      ← 形状没了
```

**所以这条改动的实际工作量不是「加两个位置」，而是两件不同的事**：

1. **补值域**（新增，从无到有）；
2. **统一形状的存法**（已有两套，且其中一套会静默出错）。

### 3.2 后果一：带形状的信息只能送给 MLIR

这不是一条要你单独决定的，它是从 §3.1 推出来的。

**推理只有三句话**：

1. 如果形状是 IR 的正式信息，那将来跟外面交换时，你手上有两种东西：**带形状的**和**不带形状的**。
2. **LLVM 只认不带形状的那种**——它的语言里没有"形状"这个词。
3. **MLIR 认带形状的那种**——它有 `tensor<2x2xf32>`。

所以：**带形状的信息只能送给 MLIR，不带形状的才能送给 LLVM。** 没有别的选项。

原因很简单——**交换只能发生在「信息还活着」的那一层**：

| 在哪一层 | 同一个矩阵乘长什么样 | 形状还在吗 |
|---|---|---|
| 张量层 | `%v = matmul %A %B [m=2][n=2][k=2]` | ✅ 在 |
| 标量层 | `fmul float %A, %B` | ❌ 没了 |

实测佐证：

```
hello.dsl  →  .ll  →  llc -march=riscv32    ✅ 通过     （没有形状）
cnn.onnx   →  .ll                           ⛔ 拒绝     （有形状）
```

**结论**：将来要跟外面交换，**上面（带形状）找 MLIR，下面（不带形状）找 LLVM**。
这个结论不用决定，它是 §3.1 的直接后果。

**它为什么算"不可逆"**：如果 §3.1 选错了（形状不算正式信息），那么"带形状的东西"
在你手里压根不存在——上游早就把它丢了。所以不可逆的**是 §3.1，不是这一条**。

### 3.3 后果二：往外送的时候什么会丢

同样是从 §3.1 推出来的：

| 信息 | 送给 LLVM 时 | 送给 MLIR 时 |
|---|---|---|
| **值域** | 可以存进 LLVM 的 `!range`（**有对应物**） | 原生 |
| **形状** | **没有对应物**，只能降成常量 + 内存布局 | 原生 |

**这条决定了"和 LLVM 组合"这条路走得通**：ScratchV 用形状和值域做完特化之后，
产出的 LLVM IR 里**值域信息以 `!range` 保留下来**，LLVM 的后端还能继续利用它
——**这不是替代 LLVM，是给 LLVM 喂更好的 IR。**

**它为什么算"不可逆"**：降级路径是**信息丢失点**。不在设计时定好"哪些能丢、丢成什么"，
跨边界的每一次传递都会静默降级，而且事后无法追查。

## 4. 超越 LLVM 的三种走法

架构要**同时容得下**这三种，而不是为某一种特化。

| 走法 | 做法 | 需要先有什么 | 难度 |
|---|---|---|---|
| **组合式** ★最先可行 | ScratchV 做 LLVM 不做的（形状特化、按值域做代数重写），产出 IR 交给 LLVM 做通用后端 | 输出 `.ll`（**已有**）+ 能接 MLIR（§6） | 低 |
| **替换式** | 用 ScratchV 的**某一层**替换 LLVM 的同层（例如用内核替掉 LLVM 的指令选择） | 层间接口对齐（§6 的目标描述/后端接口/内核钩子） | 中 |
| **端到端** | 整条链打败 LLVM | 全部 | 高，**只在极窄的域可行** |

**架构上的要求只有一条**：**不需要为"超越"单独设计任何东西。**
只要每层是**数据驱动**、**可替换**的，"超越"就是**拼装**出来的，而不是硬编码出来的。

### 4.1 通用做法：不搬框架，只写转换器

上面三种走法共用同一个做法。它值得单独说清，因为**它在这份文档里会反复出现**：

> **不在对方的框架里重写自己，只在边界上放一个转换器。**
> 转换器便宜的前提是：**两边对同一信息的表示方式已经对齐。**

**判据**：能一句话说清「边界上过的是什么」，就能借；说不清，就只能搬。

| 想借的东西 | 全搬过来的代价 | 只写转换器的形态 | 要事先对齐什么 |
|---|---|---|---|
| **MLIR 的形状 / 张量层** | 全量迁移（见 §3.1 的七块表） | MLIR ↔ ScratchV IR 双向转换 | 形状在类型里（**§3.1 选 A+C**） |
| **LLVM 的后端** | 自己写后端去追平 | 产出 `.ll` 交给 `llc` | 语义可映射到 LLVM IR 子集 |
| **LLVM 的中端优化** | 重新实现 | `.ll` 往返 `opt` | 同上 + SSA |
| **torch-mlir 的前端** | 自己写 ONNX 解析 | 吃它产出的 MLIR | 形状在类型里 |
| **平台 qemu 缓存插件** | 自己写模拟器 | 直接调用 | 成本口径一致（§7.2） |
| **内核层** | 内核写进通用编译链 | 内核调用钩子（§6） | IR 里能表达形状 |

**反过来也成立**：§6 要预留的每一条接口，本质都是「**为某一次这样的转换留位置**」。

#### 这个做法会失效的情形

**当要借的东西，其价值恰恰在于「它整体」时。** LLVM 的 pass 互相依赖、MLIR 的
dialect 互为输入——**只借一块，往往要连带背上别人的全套约定**。那时候不如不借，
或者退回去自己实现那一小块。这正是 §2 那四件事存在的意义：**在对方不覆盖的地方，
自己写反而更划算。**

#### 一个具体的例子：MLIR 的 pass 能不能只借一部分

**不能"只借 pass 不借框架"**——MLIR 的 pass 不是独立小工具，是**绑在 MLIR 自己的
IR 数据结构上的 C++ 类**。看签名就明白：

```cpp
FailureOr<scf::ForOp> tileLinalgOp(RewriterBase &b, LinalgOp op, ...);
//          ↑ scf::      ↑ mlir::     ↑ linalg::
```

参数和返回值**全是 `mlir::` 的类型**。它不认识 ScratchV 的 `Instruction` 和 `Value`。

所以「借 MLIR 的 pass」实际有三种做法，成本差一个数量级：

| 做法 | 要引入 MLIR 吗 | 需要什么 | 适用 |
|---|---|---|---|
| **移植算法**（读它的实现，用自己的 IR 重写） | 否 | 自己重写，按算法复杂度定价 | 小 pass：tiling、unroll、simplify |
| **转换过去跑一趟** | **是**（当"第二 IR"） | 定义一个自己的方言 + 写双向转换 + 接受 SSA/region 约束 | 中大型：`linalg` 全套、`affine` |
| **全量迁移** | 是（且当主 IR） | §3.1 的七块 | — |

⚠️ **这条路有滑坡**：一旦转换器写好、方言定义好、往返跑通，你会**倾向**不断扩大
它的使用范围——"再多用两个 pass 也不难"。**所以必须提前划死"MLIR 只出现在哪一段"**，
否则 §3.1 选的 A+C 会名存实亡。

**而且暂时不需要评估这件事。** 现在要做的是 §3.1（自己拿形状特化）；等真要借的时候，
要回答的不是笼统的"借 MLIR 的 pass"，而是：**具体哪个 pass、解决哪个具体问题、
自己重写要多少行**——答不出这三条，就不值得借。

## 5. 现状：ScratchV 没有「目标」这个概念

**一句话**：在 ScratchV 里，「我在给什么机器编译」这件事**没有单一出处**——
它散在十几个文件里，而且**同一个后端在不同文件里说的是不同的机器**。

### 5.1 先看矛盾本身

同一个 RISC-V 后端，"目标机器是哪一台"有三种说法：

| 文件 | 原文 | 说是几位 |
|---|---|---|
| `scratchv/backend/asm_emit.py:3` | `"suitable for riscv64-unknown-elf-gcc"` | **64 位** |
| `scratchv/backend/llvm_codegen.py:51` | `target triple = "riscv64-unknown-elf"` | **64 位** |
| `scratchv/backend/llvm_mca.py:19` | `-mtriple=riscv32` | **32 位** |

第二条在实测里撞到过（附录 B.3）：ScratchV 产出的 `.ll` 头部写 `riscv64`，
而项目实际用 `llc -march=riscv32` 编译它。**它能跑，是因为 LLVM 不校验这个字段——
不是因为它写对了。**

### 5.2 散在哪些地方（按「是什么」分组）

一共 **15 个文件**：

| 组 | 这一组回答的问题 | 位置 |
|---|---|---|
| **A · 指令集 / triple** | **给哪台机器** | `asm_emit.py:3`、`llvm_codegen.py:51`、`llvm_mca.py:19`、`onnx_to_llvm_standalone.py:446`、`compare_codegen.py:84,89` |
| **B · 寄存器模型** | **有哪些寄存器可用** | `machine_types.py:163-175`（只有整数，无浮点寄存器组）、`regalloc_linear.py:212-218`（硬校验"只收整数寄存器"）、`kernels/_scaffold.py`（**另一份** 26 个寄存器的池子，在 `main`） |
| **C · ISA / 微架构档位** | **它有多快** | `spike_sim.py`、`benchmark.py:145-165`、`llvm_cache_compare.py:487,691`、`tinyfive_compare.py`、`rv32_bench.py`、`riscv_tensor.py`、`ci_benchmark.py` |

**分组是关键**：A 组说的是"**目标是什么**"，C 组说的是"**它多快**"。
这两件事在 ScratchV 里**没有被分开**——所以既说不清"在给谁编译"，
也没法单独换掉性能模型（换指令集不该动性能模型，反之亦然）。

### 5.3 这会造成什么

**具体的痛**：内测比赛2 要加 `rv32imf`（多一个浮点寄存器组），得同时改四处，
**漏掉任何一处都不报错，只会静默产生错的代码**：

1. `machine_types.py` —— 补浮点寄存器的集合
2. `regalloc_linear.py:212-218` —— 放开"只接受整数寄存器"的硬校验
3. `kernels/_scaffold.py` —— 寄存器池加浮点部分
4. 平台侧 `march` 透传

**结构性的痛**：想换一个 target（rv32e / 带 P 扩展 / 另一种缓存几何），
**没有"一个地方"可改**——只能在十几处里再散一遍，而且每一组的散法还不一样。

### 5.4 这一节要引出什么

LLVM 对这个问题的答案是 **TableGen**：把 target 描述在**构建时**生成成 C++。
好处是有唯一真相源；坏处是**换一个 target 就得重新构建 LLVM**。

ScratchV 想做同一件事，但**做成数据而不是代码**——这就是 §2 第一条
（目标描述运行时可加载），落地形态是 §6 的第一条和 §7.1。

**为什么先做它**：它同时是三条线的交汇点——

- 内测比赛2 的 `rv32imf`
- 内核层的寄存器约束（浮点下约束从一条分裂成两条独立的）
- 与 LLVM 互换的前提（现在两边连 triple 都不是同一个）

## 6. 要预留的接口

每一条现在的最小动作都**不改变任何行为**。

| 接口 | 为哪件事 | 现在两侧是什么 | **现在的最小动作** | 将来能插进什么 |
|---|---|---|---|---|
| **目标描述** ★ | §2 第一条 | 「同一台机器」散在 15 个文件、说法互相矛盾（§5） | 抽一张表；**所有位置从它读**，取值填成各处现值 | 加 target 只改一处；运行时可加载 |
| **成本模型** ★ | §2 第二条 | `cycle_estimator.py`（周期）与内核层常量互不相识；`MISS_PENALTY` 藏在配置的环境变量里 | 定义两个类型（§7.2）；`MISS_PENALTY` 改为**显式入参**；**不接进任何决策** | 目标函数可换、可作搜索目标 |
| **形状/值域进 IR 类型** ★ | §2 第三条 | 形状有两套存法（一套会静默出错）；值域没有（§3.1） | 统一存法；补值域字段，**默认空** | 全图特化；按值域做代数重写 |
| **接 MLIR 的转换器** | §3.2 / §4.1 | 无 | 只留接口，函数体空 | 借用 MLIR 的张量层优化 |
| **后端统一接口 + 输出 LLVM IR** | §4.1 | `compiler.py` 硬编码 4 条路径（`ir`/`tensor-c`/`llvm`/`riscv`）；`llvm_codegen.py` 能产标准 `.ll` 且实测可编译 | 定后端接口；把 `.ll` 登记为正式输出 | 新后端即插即用；和 LLVM 组合 |
| **内核调用钩子** | §2 第四条 | 内核层与主线**零调用**（`grep -rn "backend.kernels"` 为空） | 后端接口上留 `specialize(IR, target) -> IR \| None`，**默认返回 `None`** | 内核收益回流主线 |
| **值域外送为 `!range`** | §3.3 | 无 | 在值域字段上标注"外送时降级为 `!range`" | 和 LLVM 组合时信息不丢 |
| **IR 可打印可解析** | 全部 | IR 只能在内存里造 | `print` / `parse` 往返 | 能对比、能落地、能跨进程 |

### 6.1 每条接口的判据

| 接口 | 判据（结构性，不比快慢） |
|---|---|
| 目标描述 | 改一处 `march`，全仓库一致地跟着变 |
| 成本模型 | 两个产物的成本口径不同时拒绝比较；`MISS_PENALTY` 不在任何全局配置里 |
| 形状/值域进 IR 类型 | 改完之后，现有产物**逐字节不变** |
| 接 MLIR 的转换器 | 接口存在且被至少一个调用点引用（实现可以为空） |
| 后端统一接口 | 加一条后端不改 `compiler.py` 的分派逻辑 |
| 内核调用钩子 | 钩子返回 `None` 时，所有现有产物逐字节不变 |
| 值域外送为 `!range` | 送出的 `.ll` 里能 grep 到 `!range` |
| IR 可打印可解析 | `parse(print(ir)) == ir` |

## 7. 两个核心类型的设计

### 7.1 目标描述

**唯一允许直接写助记符与寄存器名的地方。**

```python
@dataclass(frozen=True)
class TargetDesc:
    name: str                            # 'rv32imf'
    triple: str                          # 'riscv32-unknown-elf'
    march: str                           # 'rv32imf'
    mabi: str                            # 'ilp32'
    banks: dict[str, tuple[str, ...]]    # {'int': INT_POOL, 'fp': F_POOL}
    load:  dict[str, str]                # {'int32': 'LW',  'f32': 'FLW'}
    store: dict[str, str]                # {'int32': 'SW',  'f32': 'FSW'}
    imm_max: int                         # 2047（12 位有符号）
    line_bytes: int                      # 64（L1 缓存行）
    branch_reach: int                    # 400（条件分支 ±4KB 折算的行数）
```

**约束**：

- `banks` 的容量是**寄存器约束的唯一来源**——不许把 `26` 写进任何约束表达式。
  浮点下累加器和保留值在浮点组、指针在整数组，**约束从一条分裂成两条独立的**。
- 取值必须**逐字等于现状**，这样「现有产物逐字节不变」才可能成立。

### 7.2 成本模型

**口径的四个维度**：

```python
@dataclass(frozen=True)
class CostModelKey:
    target: str          # 'rv32imf'
    objective: str       # 'instr+miss' | 'cycles' | 'code-size' | 'area'
    measurement: str     # 'measured' | 'analytic'      ← 必须显式
    contract: str        # 'best-of-10' | 'last'
```

四个维度都**真实影响最优解**，没有一个可以省：`target` 决定指令集与缓存参数；
`objective` 决定**同一个程序的最优解不同**；`measurement` 决定数字可不可信（附录 B.3）；
`contract` 决定"重复跑"是否合法。

**接口**：

```python
class CostModel(Protocol):
    key: CostModelKey
    def cost(self, artifact, observations=None) -> Cost: ...
    def compare(self, a: Artifact, b: Artifact) -> Delta: ...
        # 实现必须校验 a.cost_key == b.cost_key，否则拒绝
```

**三条设计规则**：

1. **按口径索引，不用全局单例。** 每个 pass 把成本模型当**显式参数**收。
2. **产物记录它是在哪个口径下产生的**（`Artifact.cost_key`）——否则结果无法归因。
3. **只有「选择类」pass 能读成本模型**（下表）。

**硬边界——这条最容易被误用**：

| ✅ 该由成本模型驱动（**选择类**） | ⛔ **绝对不能**（**合法性 / 正确性类**） |
|---|---|
| 分块大小、展开因子、k 循环展开还是循环、分发方式、cache blocking、用内核还是通用、段布局填充 | 指令选择、寄存器分配的**正确性**、ABI、ISA 闸门合规、数值降低的语义 |

**右边一旦受成本模型影响，换个模型就会生成错误的代码。**

| 阶段 | 内容 | 放行条件（结构性） |
|---|---|---|
| **P0（当前）** | 预留接口：§6 的目标描述、成本模型、形状/值域进 IR 类型，其余只留空实现。**同时**：内测比赛2 三题做到「明显优于 `-O0`」 | ① 现有产物**逐字节不变**；② `.ll` 输出对 scalar 路径可用（**已实测**，附录 B.3） |

| **P4** | 组合式超越：ScratchV 前端 + 优化 → `.ll`（带 `!range`）→ `llc` | 端到端跑通一次 |

## 9. 明确不做

| 不做 | 为什么 |
|---|---|
| 改用 MLIR（全量迁移） | 大工程、收益未定义。只留 §6 的转换器接口 |
| 吃别人的 `.ll` 当**主输入** | §3.2：LLVM IR 承载不了形状，中端该接 MLIR |
| 追 LLVM 的寄存器分配 / 一般循环优化 | 追不上，且不在 §2 那四条里 |
| 指令调度器 | 通用口径下的赢面不在调度；只在特定成本模型下有意义，留作另一条口径 |

| 用 `.option rvc` | 平台 ISA 闸门判**整题 0 分** |

## 附录 A · 口径必填

**任何性能结论必须携带四个字段**，缺一不可：

```
(target, objective, measurement, contract)
```

| 字段 | 含义 | 例 |
|---|---|---|
| `target` | 指令集与缓存几何 | `rv32imf` / `rv64fd` |
| `objective` | 优化目标（成本函数） | `instr+15×L1miss` / `throughput` |
| `measurement` | **数据怎么来的** | `measured`（真跑）/ `analytic`（解析估算） |
| `contract` | 计分 / 采样语义 | `best-of-10` / `last` |

理由见附录 B——现状已经证明，缺了这四个字段的数字会被读反、被相减、被当成证据。

## 附录 B · 对比与测量（不属于上面的设计，是"现在"的事）

> 这一节可逆，不影响 §1–§9 的任何设计决定。

### B.1 三个互相矛盾的 ScratchV 数字

| ScratchV 动态指令数 | 出处 | 附带口径 |
|---:|---|---|
| **77.7 亿** | `docs/reference/ARCHITECTURE.md:286` | LLVM 侧是 rv64fd + `analytic`；同文件 §4.3 标题为「为什么 ScratchV 慢 4.4x？」 |
| **32.2 亿** | `docs/guide/03-指标解读指南.md:163` | 标注「优化后」；同表 LLVM = 18.5 亿（float32），比值 1.74x ❌ |
| **22.04 亿** | `benchmark_reports/benchmark.json` | `estimation.total_instructions`，时间戳 2026-06-22，**估算值** |

三者相差最多 **3.5×**，跨了 6 月 → 9 月两次口径变更。**本文件不判定哪个是当前真值**——
在补上附录 A 的四个字段之前，三个都不构成证据。

### B.2 LLVM 的成本模型**可以**按场景切换（实测）

本文早期草稿说「LLVM 的成本模型不能切」，**这是错的**：

```
$ llc --cost-kind=<value>
  可取值：throughput | latency | code-size | size-latency     ← 编译期固定的四个
  --force-target-instruction-cost=<uint>   # 把所有指令成本拍成一个常数
```

准确表述：

> LLVM 的成本模型**本来就按 target 可切**（TTI 是每目标的虚接口）。
> 它缺的不是「可切换」，而是 **(a) 可切集合里没有「指令数 + 缓存缺失」这一维；
> (b) 它是 pass 内部的局部查询，没有地方能说「这是我的目标函数，去搜索它的最小值」。**

这正是 §2 第二条的准确表述：**把成本模型提升成驱动搜索的一等公民**，
而不是"做一个可切换的成本模型"——后者 LLVM 已经有了。

### B.3 两条实测边界（决定了 §3.2）

| 实测 | 结果 |
|---|---|
| `hello.dsl --backend llvm` → `.ll` → `llc -march=riscv32 -mattr=+m` | ✅ **编译成功** |
| `cnn.onnx --backend llvm` | ⛔ `Codegen error: Legacy riscv/llvm backends cannot lower tensor buffers`（`compiler.py:527-531`，**与 riscv 后端同一道闸门**） |

顺带抓到现场证据：产出的 IR 头是 `target triple = "riscv64-unknown-elf"`，
而项目实际用 `llc -march=riscv32` 编译——**正是 §5.1 那个矛盾的现场**。

### B.4 需要比较时的规则

| 项 | 定义 |
|---|---|
| 输入集 | 固定模型 + hash + 固定输入张量 |
| 目标 | `(triple, march, mabi)` **两边必须完全相同** |
| 成本模型 | 命名 + 定义，**两边同一份**（§7.2） |
| 测量方法 | `measured` 优先；用 `analytic` 时两边都必须是 |
| 采样语义 | `best-of-N` 还是 `last` |
| 命令行 | 模仿 `llc`：`scratchv-llc -march=riscv32 -mattr=+m -O2 in.ll -o out.s` |

**硬规矩**：任何「超越 X%」的结论必须附上附录 A 的四个字段 + **一条可复现命令**。
