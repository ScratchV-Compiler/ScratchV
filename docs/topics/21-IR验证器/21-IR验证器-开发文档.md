## 1. 开发目标与设计衔接

### 1.1 交付目标

实现只读验证器，接收 `Program`，输出结构化诊断；明确区分 ERROR 和 WARNING，提供规则名、函数、块、指令索引、值名和阶段信息。在开启 `--verify-ir` 后，验证前端产生的共享 Program、每个 IR 优化 pass 的输入与输出，以及后端输入。接受项目已有的合法 FOR/ENDFOR，不要求前端先将其改写为 BR/BR_IF。ERROR 阻止后续编译，WARNING 不阻止编译。

七条规则的编号和语义沿用设计文档：

| 规则 | 主要实现内容 | 依赖 |
|---|---|---|
| R1 def-before-use | 名称解析、直线片段顺序、跨片段支配 | 定义表；跨片段检查还依赖有效 CFG，包含原块内循环路径 |
| R2 label-existence | 块名唯一性与跳转目标存在性 | 块索引、分支字段解析 |
| R3 block-termination | 空块和块尾终止检查 | 终止指令集合 |
| R4 type-consistency | 指令签名、dtype、常量及引用类型 | 签名表；部分检查依赖唯一定义 |
| R5 control-flow-integrity | 非法分支结构、终止后指令、不支持的表示、不可达块 | 局部扫描；可达性还依赖有效 CFG |
| R6 ssa-validity | 全局、参数、指令结果名称冲突 | 定义表和首次定义位置 |
| R7 entry-existence | 函数至少有一个块 | 函数块列表 |


### 1.2 职责与范围

CFG 模块负责解释控制流、建立图和维护原 IR 位置映射，复用上游 FOR/ENDFOR 的循环建边能力。验证器负责七条规则、错误等级和诊断，调用 CFG 的建图及分析结果。

前端、IR 类型和 Builder 直接复用，不要求前端转换 FOR/ENDFOR，不修改输入 Program。

循环规则写入 R1/R3/R4/R5，常量与 dtype 约定写入 R4，位置去重机制写入诊断部分；这些内容是正式实现要求，不单列讨论决定。完整 PHI、形状推导、优化等价性及运行时安全证明不属于本次范围。

### 2.2 上下游约定

- 上游：直接使用现有前端产生的 Program，既可以包含显式分支，也可以包含合法 FOR/ENDFOR。参数、全局值和指令定义按实际字段读取，不猜测或补齐未登记的定义。
- 验证器：不替上游补参数、补 RETURN、拆块或重命名值；发现不支持表示时明确失败。
- CFG：创建只读控制流图，不改 Function.blocks 或原指令；返回图、原位置映射和可定位的结构问题，由验证器转换为对应规则诊断。
- IR 优化：输入、输出都接受同一套规则；验证输出时使用 pass 实际返回的 Program，不再检查旧对象。
- 下游：只有验证通过才进入 LLVM/RISC-V 后端。`--verify` 的数值结果比对与 `--verify-ir` 的结构检查分开，不复用同一个配置字段。
- 输出：在最后一次 IR 验证成功之前，不以写模式打开目标文件，不提前清空原有文件。


## 3. 核心实现方案

### 3.1 公共 API 与诊断构造

公共 API 保持设计文档 2.5 节的 ErrorLevel、VerificationError、IRVerifier.verify(stage=...)、verify_ir(program, stage=...)。

`verify_ir` 只包装验证结果：

```python
issues = IRVerifier(program).verify(stage=stage)
passed = not any(issue.level is ErrorLevel.ERROR for issue in issues)
return passed, issues
```

消息使用统一内部 `_emit(...)` 构造，不在各检查函数里 print。公开 issue 字段保持设计不变；内部另外记录位置序号和原因键，用于排序、去重。

内部原因键采用 `undefined-value`、`use-before-definition`、`not-dominating`、`duplicate-definition` 等固定字符串。它们不是新增对外规则，不替代七条 rule 标识，也不要求用户依赖中文消息做程序判断。

### 3.2 分析数据结构

这些结构分别保存“值从哪里来”“执行路径是什么”“问题在哪里”。它们是分析记录，不是目标程序的运行时变量，也不新增到 IR 对象中。类型名是拟议名称，不要求每一项都实现为独立类。

| 结构 | 所属模块 | 关键字段与作用 |
|---|---|---|
| IRLocation | 共用位置约定，随 CFG 结果传递 | kind、function_order、block_order、instruction_index、item_index；区分指令、参数、全局值等真实位置，不依赖名称唯一 |
| Definition | 验证器 | name、kind、dtype、location、定义指令引用；记录参数/全局/结果的来源，支持 R1/R4/R6，不保存运行时计算结果 |
| FunctionContext | 验证器 | function、blocks_by_name、definitions、ambiguous_names、CFG 分析结果；组织一轮函数检查的数据 |
| ControlFlowGraph | 上游 CFG | build_cfg(IRCFGAdapter(func)) 返回；验证器维护原始位置到节点的关联，调用 verify_cfg 与 compute_dominators |
| LoopRegion | CFG | FOR/ENDFOR 位置、父循环、循环变量；先记录配对，建图成功后关联初始化/条件/回边节点，不要求失败的配对记录已有完整图节点 |
| ResolvedOperand | 验证器 | kind、definition、constant_status；统一表达具名引用、字面量、未定义或歧义，可作为辅助函数返回值，不必全量缓存 |
| LocatedIssue | 验证器 | issue、location、reason_key；公开错误内容与内部精确位置分离，支持排序与去重 |

`blocks_by_name` 保存同名块的全部序号，例如 `dict[str, list[int]]`，不能用后一个块覆盖前一个。`definitions` 保留首次定义，重复名字加入 ambiguous_names，同时分别记录后续冲突位置。

位置映射有两个方向：原指令位置到 CFG 节点，用于查询定义和使用所在路径；CFG 节点到原指令范围或控制流标记，用于把分析结果还原为用户可见位置。一个原块可以对应多个 CFG 节点，循环初始化和条件等合成节点也要关联其来源 FOR。参数和全局值没有指令节点，用各自列表中的 item_index 区分。

每次 verify 都新建验证上下文，并取得当前 Program 的新 CFG 结果，不跨 pass 复用失效数据。键使用不可变位置记录、字符串或整数序号，不把可变 Value 当作键，也不给 BasicBlock 添加动态属性。

排序约定：全局诊断在函数诊断之前；函数级在该函数各块之前；块级在该块指令之前。然后依设计按指令索引、规则编号、值名、消息排序。没有位置时内部用 -1 排序，公开字段仍为 None。

去重键包含 `(location, rule, value_name, reason_key)`，location 包含位置种类与对应序号。名称用于展示，内部序号用于区分真实位置：不同块即使同名也分别保留；多个参数或全局冲突也不因块/指令字段都是 None 而合并。一个错误被不同辅助函数重复发现才去重。重名时可在消息中补充序号，不改变公开诊断字段。

### 3.3 调度流程与错误抑制

入口控制流程如下，待实现伪代码：

```text
verify(program):
  创建空诊断收集器
  检查并索引全局值
  对每个函数：
    创建上下文
    若没有块：报告 R7；继续下一函数
    索引块名：检查 R2
    索引参数及所有 dest：检查 R6
    调用 CFG 模块的结构扫描，取得循环配对及结构问题
    将结构问题映射为 R5；结合片段边界检查块尾和终止后指令：R3/R5
    解析分支并核对目标：检查 R5/R2
    解析操作数、检查签名和类型：检查 R4
    若 CFG 结构有效：
      调用 CFG 模块建立完整图和位置映射；检测显式入口入边
      若仍有效：调用 CFG 可达性及支配分析，依据结果报告 WARNING
    检查未定义名称、直线片段顺序及可执行的跨片段支配检查：R1
  去重、排序，返回诊断
```

类型错误、重复定义不必阻止独立的块尾检查；但重复块名、缺失目标等会破坏图结构，必须禁止依赖该图的分析。

| 已发现问题 | 跳过什么 | 仍检查什么 |
|---|---|---|
| 无块 | 该函数的块相关检查 | 其他函数和全局值 |
| 重复块名、目标缺失、循环配对错误、非法终止结构、显式入口入边、其他不支持表示 | 本函数可达性、支配关系 | 局部结构、签名、定义冲突、名称存在；无循环分隔的直线片段内顺序 |
| 名称重复定义 | 该名称依赖唯一来源的类型/支配判断 | 其他名称及该指令的独立签名错误 |
| 参数数量错误 | 依赖不存在下标的检查 | 实际存在的操作数、其他指令 |
| 未命名来源的常量元数据非法 | 对该字面量附加“未定义”诊断 | R4 常量错误及其他独立问题 |
| 不可达块 | 以入口为依据的跨块支配检查 | 名称存在、同块顺序、类型、SSA、块结构 |

对于有显式定义但常量元数据非法的名称，名称仍先解析为具名引用；元数据错误不能掩盖真实的先使用后定义。这里抑制的是没有帮助的衍生“未定义”，不是取消所有 R1 检查。

### 3.4 R2、R3、R5、R7：先完成结构检查

显式基本块终止集合为 `{BR, BR_IF, RETURN}`。FOR/ENDFOR 是具有隐式循环边的结构标记，不是普通算术指令，也不能作为“出现后禁止任何指令”的显式终止指令处理。

分支目标解析只返回局部分析结果，不修改 `instr.target`：

- BR：目标须是非空字符串，核对当前函数索引；无目标归 R2。
- BR_IF：拆分逗号后保留空项，去除各项首尾空白；恰好两项且均非空，才继续 R2。格式错误归 R5。
- 两个相同目标合法；原始两个出口都验证，建邻接集合时可以去重。
- 空白块名按空名称处理；块定义名以原字符串为标识，不自动重命名或规范化。命名端应避免首尾空白，避免目标 trim 后无法匹配。

不含结构化循环的块，R3 仍检查空块和块尾 BR/BR_IF/RETURN。含 FOR/ENDFOR 时，按循环标记拆出的分析片段检查出口：FOR 提供进入/退出路径，ENDFOR 提供回边，它们不要求前端再插一条 BR。循环之后的普通片段仍须有合法结束方式，不能把结构化循环支持变成任意块之间的隐式落入许可。

R5 只对显式 BR/BR_IF/RETURN 检查其后的普通指令，定位第一条多余指令；FOR 后有循环体、ENDFOR 后有继续执行的代码本身不是错误。RETURN 后 ADD 同时报告 R3/R5 的用例保持不变。

FOR/ENDFOR 是合法指令；R5 检查配对、嵌套与控制流结构，不因 opcode 出现而失败。配对与建图由 CFG 模块统一提供，验证器不维护另一套循环解析逻辑：

1. **CFG 结构扫描。** 按函数 blocks 列表及各块 instructions 顺序读取标记，维护循环栈；FOR 入栈，ENDFOR 匹配最近的未闭合 FOR。保存父循环和原位置，支持嵌套及跨块配对。孤立 ENDFOR、未闭合 FOR 以带位置的结构问题返回，由验证器映射为 R5 ERROR；函数之间不共享栈。这个顺序只定义结构配对，不自动赋予普通相邻块执行边。普通显式控制流的块重排测试与结构标记顺序测试分开，不能任意重排跨块标记后仍要求配对不变。
2. **CFG 完整建图。** 在 FOR 前后、ENDFOR 前后及显式分支处划分分析片段；建立初始化、条件、循环体、回边和出口节点。条件有进入循环体和跳过循环体的两条边，ENDFOR 回到条件节点。循环变量的静态定义关联初始化节点，回边不制造第二条 IR 定义。嵌套循环分别建边，原块、原指令和变量字段不改变。

CFG 模块返回一张包含普通分支与结构化循环的完整图，不把两部分分别分析。原块入口映射到第一个分析节点；BR/BR_IF 从所在片段指向目标块入口；RETURN 不添加后继。原块被拆分后以片段重新构造边，不能叠加旧整块出边。ENDFOR 后的位置作为循环退出续接点，空循环也保留条件到回边和条件到出口两条路径；没有合法续接位置时返回结构问题，不能凭空补 RETURN。

验证器读取 CFG 返回的图和位置映射，调用可达性及支配分析，不自行新增节点或边。可达子图视图由验证器筛选后交给上游支配算法，不修改原图或 Program。普通分支进入循环体时仍按真实边分析，不能假定必然经过初始化；定义不支配使用由 R1 报告。

原始结构扫描由验证器完成，上游 verify_cfg 返回图诊断，不直接依赖 VerificationError。验证器负责规则、等级和诊断消息。结构非法时不把部分图交给支配分析，局部错误仍继续收集。新增循环能力和映射需回归普通显式分支的接口及边集合，不能只检查节点数量。

循环可能执行零次，因此不能把循环体内的定义自动视为循环后可用。初版不靠展开循环或常量迭代次数推断来省略零次路径。回到 CFG 的循环条件节点不等于显式跳转原函数入口，不能误触发入口入边错误。原块只要包含可达片段就不能整块标为不可达；原块级 WARNING 仅在该块所有可执行片段均不可达时产生。

LABEL 与非空 phi_nodes 暂沿用原支持边界，报告明确的“本验证入口暂不支持”R5；不称为这两种 IR 表示天然非法。这不影响合法 FOR/ENDFOR 的支持，也不再使用将四者混为一谈的旧 U42。

### 3.5 R6 与 R1：定义表、解析和支配

定义表先登记全局、再登记本函数参数、再扫描所有块的 dest。不登记 locals 作为定义，不把常量操作数登记为定义。重复时保留第一次位置，后续每个重复定义各报一次 R6；将名字加入 ambiguous_names。全局重复只在全局层报告一次对应冲突，不因函数数量而重复输出。

操作数解析顺序：

1. 名称已歧义：返回 ambiguous，避免任意选择来源。
2. 存在显式定义：返回具名引用，常量标记不改变定义位置。
3. 无显式定义且标记为常量：检查元数据，返回合法 literal 或 invalid_literal。
4. 其余返回 undefined，由 R1 报错。

对于具名结果：定义与使用在同一直线分析片段时要求 `def_index < use_index`；跨片段时要求定义节点支配使用节点，即使二者都属于原来的同一个 BasicBlock。参数和全局值直接可用。检查使用关系时不能先把当前 dest 放入一个“已定义集合”再处理操作数。FOR 的循环变量按初始化定义处理；循环体中的普通值经过零次循环路径后不自动可用。

调用 CFG 的可达性遍历和支配计算，只对可达子图求支配；入口集合始终固定为自身。通过 CFG 返回的位置映射输出诊断，不把合成节点名称当作用户基本块名。一个可达非入口节点至少有一个可达前驱；异常空前驱应视为内部图契约被破坏，不能把空交集解释为自动通过。

例子：left 定义 x，right 不定义 x，两边都跳 merge。Dom(merge) 不包含 left，因此 merge 使用 x 报 R1，而不是因为 left 在块列表更靠前就通过。

### 3.6 R4：集中签名与常量边界

建议用 OpcodeSpec 保存操作数数量范围、是否需要 dest、允许类型族和专门检查函数。普通指令签名沿用设计 3.4 节，增加 FOR/ENDFOR 的合法签名，不在不同辅助函数里各写一套数量表：FOR 无普通操作数、有 i32 循环变量结果，start/end/step 按现有 Builder 的整数属性表示检查；ENDFOR 无操作数、无结果。属性缺失、错误类型或无效步长应给出具体 R4，而不是将整类 opcode 判成不支持。控制流配对错误则归 R5。步长方向及边界取现有指令语义，不以 Python range 的全部能力擅自扩展后端语义。

检查顺序：

1. 是否为本入口支持的 opcode；不支持的控制流已交给 R5。
2. 操作数数量与 dest 有无；结构错误之后只跳过依赖该结构的类型检查。
3. 实际存在的 Value.dtype 必须是 DataType.FLOAT32、INT32、FLOAT64、INT64 之一；字符串 "f32" 等不得自动转换。非法类型报告 R4 后跳过依赖该类型的兼容判断。
4. 输入之间、输入与结果之间的类型关系。
5. 同名引用的 dtype 是否与唯一定义相同。
6. 常量、比较操作符、返回签名、已知存储来源等专门约束。

LOAD/STORE 只能针对已知 ALLOCA 来源检查元素类型；不把所有 f32 值都当作 f32 指针，也不扩展为内存安全证明。Function.returns 是类型签名，不参与 R1 的操作数遍历；空 returns 按设计表示未声明返回签名，不应擅自解释为必须无返回值。

整数常量须排除 bool，检查有符号位宽范围。所有输入、结果和全局/参数中的 dtype 都应检查，包括从未被使用的值。常量元数据也不能只在被使用时才检查。

**常量一致性检查：** 先检查各自的类型合法性；整数和普通浮点数精确比较，不使用 isclose 或误差容限；两个 NaN 视为元数据一致；Inf 要求符号一致；+0.0 与 -0.0 视为不一致。不检查 NaN payload，也不宣称已按目标 f32 舍入。这里比较的是 LOAD_CONST 的 attrs['value'] 与结果 Value.const_value 两份编译期记录，不是程序执行前后的内存值；不一致报 R4，不自动选择一份覆盖另一份。

遇到 attrs 缺失先产生 R4，不直接下标取值。NaN 的检查与比较使用专门辅助函数，不用宽泛 try/except 把所有内部程序错误包装成“非法 IR”。

### 3.7 API 输出示例

对于 `main` 的 entry 第 0 条使用尚未定义的 x，之后才定义 x，其余内容合法：

```text

level = ERROR
```

## 4. 编译流程集成

### 4.1 配置与诊断传递

在 CompilerConfig 中使用 `verify_ir: bool = False`；CLI 的 `--verify-ir` 映射到这一字段，与 `verify`、DEBUG 日志独立。不要仅解析参数但遗漏 args_to_config 的传递。

建议由驱动维护本次编译的验证诊断列表。检查点 `_check_ir(program, stage)` 调用验证器，将 ERROR/WARNING 分别转为现有 CompileResult.errors/warnings 可展示的文本；必要时另加专用 `ir_diagnostics` 字段保存结构化对象，不直接混用可能由其他诊断系统消费的 diagnostics 字段。新增字段必须有默认值，兼容原有构造调用。

检查点失败可以使用私有 IRValidationFailed 异常携带结构化 issues，由编译边界转换为失败结果。不要在错误收集函数里调用 sys.exit，也不要将 ERROR 降为普通 warning。CLI 只在最外层把失败结果转成非零退出码。

### 4.2 pass 管线接入方式

PassManager 是通用容器，不能给所有汇编/机器指令 pass 强行套 Program 验证。建议增加可选的 before_pass / after_pass 回调，默认 None；仅在 IR 优化管线且开启验证时绑定检查点。回调名称为拟议接口，实施时按项目风格确定。

调用顺序：

```text
after-parse
before:pass1
pass1.run(program)
after:pass1（检查 result.data）
before:pass2
pass2.run(result.data)
after:pass2
before-codegen
codegen
write output
```

如果 pass 自身失败或返回 data=None，按 pass 失败处理，不再把 None 交给验证器。若约定为 Program→Program 的 pass 却返回其他类型，应作为编译管线契约错误停止，不能跳过验证继续后端。

必须覆盖两种 pass：原地修改并返回原 Program，以及返回全新 Program。适配器也必须消费当前传入数据，不能一直持有最初的 Program。验证异常若经过通用 pass 异常处理，应保留 stage 和诊断，不能丢成一条没有位置的普通失败消息。

### 4.3 文件保护与入口验证

所有 IR 验证发生在代码生成与输出打开之前；失败立即返回。这样既保证新文件不会出现，也保证已有输出不被清空.

库接口、命令行入口都必须经过相同检查点。无优化时仍执行 after-parse 和 before-codegen。关闭验证时回调不绑定、验证器不调用；不要通过关闭日志伪装成关闭验证。

### 5.2 可落地的对象构造示例

以下测试示例针对待实现的目标 API，不表示当前实现已经通过。不使用 builder 的隐式行为，确保错误由测试精确控制。

```python
from scratchv.ir.types import (
    Program, Function, BasicBlock, Instruction, Value, DataType, OpCode,
)
from scratchv.analysis.ir_verifier import verify_ir, ErrorLevel


def make_straight_program():
    p = Program()
    a = Value("a", DataType.FLOAT32)
    x = Value("x", DataType.FLOAT32)
    y = Value("y", DataType.FLOAT32)
    f = Function("main", params=[a])
    b = BasicBlock("entry")
    b.add(Instruction(OpCode.ADD, dest=x, operands=[a, a]))
    b.add(Instruction(OpCode.MUL, dest=y, operands=[x, a]))
    b.add(Instruction(OpCode.RETURN, operands=[y]))
    f.add_block(b)
    p.add_function(f)
    return p, b


def test_u01_legal_straight_program():
    p, _ = make_straight_program()
    passed, issues = verify_ir(p, stage="after-parse")
    assert passed
    assert issues == []


def test_u03_use_before_definition():
    p, b = make_straight_program()
    b.instructions[0], b.instructions[1] = (
        b.instructions[1], b.instructions[0]
    )
    passed, issues = verify_ir(p, stage="after-parse")
    assert not passed
    assert len(issues) == 1
    issue = issues[0]
    assert issue.level is ErrorLevel.ERROR
    assert issue.rule == "def-before-use"
    assert issue.function_name == "main"
    assert issue.block_name == "entry"
    assert issue.instruction_index == 0
    assert issue.value_name == "x"
    assert issue.stage == "after-parse"
```

### 5.3 完整程序测试数据

将设计 5.3、5.4 节的伪 IR 转为 IR 对象测试数据，连同上节直线程序形成三种基本图形：

| 测试程序 | 测试意图 | 合法版输出 | 单点变异后的输出 |
|---|---|---|---|
| straight | 顺序与类型 | True，[] | 交换两条计算指令：一个 R1，entry 索引 0 |
| absdiff | 两分支、合流、ALLOC/STORE/LOAD | True，[] | merge 的 LOAD 改成使用 left 的 x 进行合法同类型计算：一个 R1，merge 索引 0 |
| repeat | 循环与支配 | True，[] | body 的回边从 header 改为入口：R5 ERROR，不继续图分析 |

absdiff 变异时保留 result 的定义及 RETURN，避免顺带制造未定义 result 或签名错误。repeat 不运行循环，只验证结构，测试不依赖其数值终止性。

另加结构化循环测试数据，直接接受现有 IR 表示，而不是先转换输入：

```text
fun loop_demo():
  entry:
    i: i32 = for [start=0] [end=3] [step=1]
    x: i32 = add i, 1:i32
    endfor
    return
```

预期 `passed=True, issues=[]`。i 在初始化位置定义一次；循环体重复执行不产生 R6。将 return 改为 `return x` 后，预期 R1：循环条件有直接退出路径，x 的定义不支配循环之后的使用，即使这两条指令原来都在 entry 内。这里采用保守结构分析，不通过常量循环次数证明必执行。

### 5.4 类型签名参数化

按签名类别组织测试，避免 opcode 与 dtype 的全笛卡尔积。每个 opcode 保留一次合法输入检查，并通过独立契约表核对其签名登记；操作数数量和 dest 边界由每类签名的代表指令检查。T/F 类型族分别以 ADD/EXP 覆盖四种 dtype。FOR、BR_IF、RETURN、LOAD_CONST、存储类型等专门语义继续用独立反例覆盖。

数量边界覆盖最少值减一、合法最少值、合法最多值、最多值加一；CONCAT 没有固定最大值，测 0、1、多个输入。CONV/GEMM 按三操作数契约测试，不新增前端偏置规范化任务，也不在验证器测试里偷偷补齐。FOR/ENDFOR 增加结果、属性、参数数量测试，与 R5 的配对测试分开。

### 5.6 集成测试的具体观测方式

- 用列表记录 `check(stage)`、`run(pass)`、`codegen`、`write` 事件。两个 pass 正常时，恰有 6 个验证阶段；无优化时恰有 2 个。重复命名 pass 建议在内部事件中保留序号，公开 stage 仍可使用 pass 名。

### 5.7 只读性、快照与规模

快照记录函数、块、指令的顺序与所有相关字段，包含 params、returns、locals、global_values、phi_nodes、attrs、target、shape 和常量元数据。不能只比较 dump。比较时对 NaN 做规范化表示，否则即使未修改也可能比较失败；同时记录原对象身份与容器成员身份，检查验证没有替换节点。

## 7. 风险与后续维护

| 风险 | 控制措施 |
|---|---|
| 把合法 FOR/ENDFOR 当成错误或普通直线指令 | CFG 模块补齐循环路径，验证器依据结构问题和分析结果检查，不要求改造前端 |
| 把列表顺序当成控制流 | 使用显式图和支配分析，以非入口块重排测试防回归 |
| 同一根因导致海量报错 | 仅抑制依赖已失效前提的检查，独立错误仍保留 |
| 集成只检查旧 Program | 强制测试返回新对象的 pass，并核对适配器输入 |
| 与数值验证混淆 | 分开配置、API、结果说明及测试 |
| 测试依赖过重 | 核心测试直接构造 IR，真实前端/后端回归分层执行 |
| 后续 opcode 增加但签名遗漏 | 对 OpCode 枚举检查：每项必须有签名或明确“不支持”分类 |
| 支配算法规模增长 | 先记录可信基线，再独立优化算法，保持同一组正确性测试 |
