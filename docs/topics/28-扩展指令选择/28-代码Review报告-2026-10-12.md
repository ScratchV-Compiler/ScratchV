### R1：LLVM 报告编译成功，生成的文件却不能用

#### 发生了什么

输入下面这个程序，要求计算两个整数的和：

```text
a = const(7,dtype:i32)
b = const(3,dtype:i32)
r = add(a,b)
return r
```

编译器选择 LLVM 后端时，合理的结果有两种：支持这段整数计算，生成可用的代码；或者明确说明暂不支持，并返回失败。修复前却返回了 `success=True`，错误列表也是空的，生成的 `.ll` 文件无法被 LLVM 读取。

不启用 `use_extended_isel`，分别使用 `none/basic/all` 三个优化级别，可以看到这些错误语句：

```llvm
; none
%v_1_1 = fadd i32 7, 0.0
; basic / all
%v_3_1 = fadd i32 10, 0.0
```

这里 `i32` 表示整数，`fadd` 却是浮点加法指令。也就是说，编译器把整数交给了只能处理浮点数的指令。优化器即使先把 `7+3` 算成 `10`，后端仍用错误的指令表示这个整数，文件依然无效。

用 `llvmlite.binding.parse_assembly(...).verify()` 检查，得到 `floating point constant invalid for type`：这条语句中的浮点常量不能用于指定的整数类型。[LLVM 对 fadd 的类型要求](https://llvm.org/docs/LangRef.html#fadd-instruction)

#### 为什么会出错，和本课题有什么关系

本次修改让前端能够读入带类型的常量，也让 IR 正确保留整数类型。但 LLVM 生成代码的部分仍按浮点数处理常量和四则运算，前后两部分没有一起更新。

这些前端和 IR 代码由多个后端共用。因此，即使没有打开 `--extended-isel`，整数输入也能进入 LLVM。入口原来只拒绝 LLVM 不支持的 `rem/min/max/abs/sqrt` 等扩展操作，没有拦住这里的整数常量和整数加法。

相关位置：[dsl_parser.py](../../../scratchv/frontend/dsl_parser.py#L170) 读取带类型的 `const`；[builder.py](../../../scratchv/ir/builder.py#L105) 保留运算结果的类型；[onnx_parser.py](../../../scratchv/frontend/onnx_parser.py#L182) 把 Add/Mul 交给 IR 优化器。遗漏的适配位于 [llvm_codegen.py](../../../scratchv/backend/llvm_codegen.py#L221) 的算术输出，以及第 270 行的 `_emit_load_const`。

**课题要求扩展 RISC-V，不要求同时完成 LLVM 整数后端。但我们修改了共用的输入处理代码，就需要保证 LLVM 对不支持的输入明确报错。** 否则，调用者会相信“编译成功”，直到把文件交给后续工具才发现不能用。

#### 和旧代码相比，哪里变差了

还测试了一个通过 `onnx.checker.check_model` 检查的 ONNX 模型：两个 INT32 标量常量相加。这排除了“输入模型本身不合法”的解释。

| 同一个合法 ONNX INT32 Add 模型 | 旧代码 `f3af99d` 的输出能否被 LLVM 读取 | 审查代码 `2dc976c` 的输出能否被 LLVM 读取 | 两边编译器报告 |

旧代码在前端先用 Python 算出了常量结果，部分优化路径因此绕开了问题。本次把计算统一交给 IR 优化器后，原来能输出合法 LLVM 文本的 `basic/all` 路径也开始失败。

需要区分两件事：旧代码的 `none` 本来就有这个问题；旧代码的 `basic/all` 能通过 LLVM 解析，也只能说明文件格式有效，不能据此认定 ONNX 返回值的类型完全正确。

#### 我们怎么修复

原审查提出两种办法：补上正确的 LLVM 整数代码生成，或者明确拒绝当前不支持的操作。我们按本课题范围采用了第二种办法。

1. [compiler.py](../../../scratchv/compiler.py) 在读取输入之后、优化之前检查 LLVM 是否支持这些操作和类型。当前 `load_const/add/sub/mul/div/neg` 的 LLVM 实现只支持 f32/f64；遇到 i32/i64 就返回 `success=False`，说明不支持的操作、类型及所在函数和基本块。即使整数常量没有被使用、后续可能被优化掉，也在这里明确拒绝，三个优化级别的行为一致。
2. [llvm_codegen.py](../../../scratchv/backend/llvm_codegen.py) 的 `emit()` 也执行同一检查，直接调用代码生成器时同样受保护。`save()` 先生成完整文本，再打开输出文件；输入被拒绝时，不新建文件，也不清空已有文件。
3. 检查针对具体操作。已有的整数循环控制、比较、读写内存和返回仍可使用。前端继续保留正确的整数类型，IR 优化器继续遵守 RV32 的整数计算规则。

如果以后补 LLVM 整数除法，还需要单独处理除零和溢出。直接输出 `sdiv` 不能保证 RV32 在这些情况下的结果，因为 LLVM 将相应情况定义为未定义行为。[LLVM 对 sdiv 的要求](https://llvm.org/docs/LangRef.html#sdiv-instruction)

### R2：两个函数里的同名变量，被编译器当成了同一个

#### 发生了什么

`f0` 和 `f1` 是两个不同的函数。它们各自有一个内部变量叫 `v_1`，这是合法的，就像两个函数都可以有自己的 `x`。问题在于，修复前编译器只记住了名字 `v_1`，没有记住它属于哪个函数。

最小例子是：用两个独立的 IRBuilder 分别创建 `f0`、`f1`。每个函数都申请一块局部内存（`alloca(1)`），存入常量，再读出并返回。两个构造器都从头编号，所以都会生成 `v_1/v_2/v_3`。把两个函数放进同一个 Program 后，`verify_ir(program)` 返回 `(True, [])`，确认这个输入合法。

| 两个函数的类型 | 应该发生什么 | 修复前 naive / greedy / linear 三种分配方式的结果 |
|---|---|---|
| `f0:f64`、`f1:f64` | 每个函数使用自己的局部内存 | 都失败：`local access has no layout entry: -8`，即找不到第一块局部内存的布局记录 |
| `f0:f64`、`f1:f32` | 同名变量分别属于各自函数，可以有不同类型 | 都失败：`virtual register v_2 has conflicting width or class`，即误以为同一个变量出现了两种类型 |

#### 为什么会出错

局部内存记录用变量名作字典键。第一个函数的 `v_1` 记录在 `-8`，第二个函数的 `v_1` 记录在 `-16`；后写入的记录覆盖了前一条。第一处访问还指向 `-8`，但编译器已经找不到它对应的布局信息。

类型记录也只按变量名查找。处理 `f0` 的 `v_2` 时记下 f64，再处理 `f1` 的 `v_2` 时看到 f32，于是报“类型冲突”。实际上它们是两个变量，没有冲突。

相关位置：[inst_select_ext.py](../../../scratchv/backend/inst_select_ext.py#L245) 第 252–254 行记录局部内存；[allocation.py](../../../scratchv/backend/allocation.py#L71) 的 `collect_register_types` 收集类型。两处都没有区分同名值来自哪个函数。

旧的多函数测试没有发现问题，因为它们共用一个 IRBuilder，编号一直递增，两个函数拿到的名字不同。专门测寄存器不够用时保存数据到栈上（spill）的测试，也预先给变量名加了函数前缀，避开了重名情况。

#### 影响和课题关系

合法的多函数 IR 会编译失败。当前 DSL/ONNX 入口通常只生成一个函数，因此这个问题通常不会出现在普通单函数编译中。

课题没有要求调用者把所有函数的内部变量改成全程序唯一。我们新增的局部内存和类型记录需要正确区分函数，才能让已有的多函数输入继续工作，这属于本次实现需要处理的错误。

#### 我们怎么修复

在把不同函数的机器指令合到一起之前，先给它们的内部变量生成不会重复的后端名字。可以理解为给名字补上“属于哪个函数”的身份。调用者仍可在每个函数里使用 `v_1`。

1. [instruction_select.py](../../../scratchv/backend/instruction_select.py) 在每个函数完成指令选择后，为该函数所有虚拟寄存器的定义和使用统一换名。源 IR 值、函数参数、函数内加载的全局常量和临时值都使用同一套映射。新名字避开已有名字，并保留寄存器类别和位宽。
2. [inst_select_ext.py](../../../scratchv/backend/inst_select_ext.py) 同时更新 `local_slots` 中的名字，完成后才处理下一个函数。局部内存、类型表、寄存器安排及 spill 记录因此能识别同一个变量，不会相互串用。
3. 真正的栈空间仍由后续布局步骤按函数分别安排。换名只修改后端机器指令，调用者传入的 IR 保持原样；单函数程序的命名方式保持原样。重复运行同一个选择器，也会得到稳定的名字和局部内存记录。

只修改局部内存字典是不够的。如果类型表或寄存器分配仍只看原来的 `v_1`，另一个报错还会存在。

### R3：用来核对结果的执行器，读错了浮点常量

#### 发生了什么

项目中的 `IRTraceExecutor` 可以直接计算 IR 的结果，用来和编译后的程序核对。修复前，同一个常量在编译后的程序里是 1.0，在这个执行器里却成了 0.0。

例子如下：

```python
b.ret(b.load_const(0.0, T.FLOAT32, bit_pattern=0x3f800000))
```

这条常量同时带了两份信息：数值字段写着 `0.0`，`bit_pattern` 字段写着 `0x3f800000`。后者是浮点数的原始二进制编码，在 f32 中表示 **1.0**。

本次新增的规则明确规定：提供了 `bit_pattern` 时，以这个编码为准。因此这个合法 IR 应返回 1.0。把辅助数值字段故意写成 0.0，是为了检查每个读取入口是否遵守同一规则。

| 类型 | 编译后的程序在 QEMU 中实际返回 | IRTraceExecutor 返回 |
|---|---|---|
| f32 | `0x3f800000`，即 1.0 | `0x00000000`，即 0.0 |
| f64 | `0x3ff0000000000000`，即 1.0 | `0x0000000000000000`，即 0.0 |

三种寄存器分配方式的编译结果都返回了正确值。所有 QEMU 场景的浮点异常标志 `fflags` 都是 0；这个例子只是把 1.0 读成了 0.0，没有涉及复杂的舍入或浮点异常。

#### 为什么会出错

编译器生成目标代码时已经优先读取 `bit_pattern`，核对结果的执行器却仍从旧的数值字段取值。于是，两边对同一个输入的理解不同。

相关位置：[types.py](../../../scratchv/ir/types.py#L118) 增加 `Value.bit_pattern` 并规定它优先；[rv32_emulator.py](../../../scratchv/simulator/rv32_emulator.py#L470) 的 `_resolve` 和第 577 行 `_op_load_const` 没有同步修改。一个入口负责读取运算中的常量，另一个负责执行常量加载，两处都需要修复。

#### 影响和课题关系

核对工具读错输入后，可能把正确的编译结果判为错误，也可能让某些错误没有被发现。本次 QEMU 验收没有用 `IRTraceExecutor` 作为预期结果来源，所以那些执行测试仍然通过。

本课题增加了浮点常量的表示方式，也更新了这个核对工具。它需要按同一规则读取常量，才能继续可靠地核对结果。这属于本次修改的配套修复；修复范围是读准常量，不需要把它改成完整的浮点硬件模拟器。

#### 我们怎么修复

两个读取入口使用同一个解码函数：先把编码按 uint32/uint64 保存，再用 NumPy `view` 把同一组二进制位解释成 f32/f64。这个操作只改变解释方式，不重新计算数值，因此能保留负零和 NaN 的原始编码。NaN 表示“非数值”，其编码里还可以包含额外信息。

1. 有明确编码时按编码读取；没有编码时，保留原来的 i32/f32/f64 数值转换。布尔值、非整数、超出位宽的编码，以及把浮点编码用于整数类型的输入，都会报错。
2. 加载常量时先读指令属性中的编码，缺省时再读结果 Value 的编码。两处都提供但不一致时，在修改执行状态前报错。这和生成目标代码时的规则一致。
3. 编码只写在加载指令上时，执行器记住这次定义的编码，后续返回或参与运算也使用它。记录在每次运行和每个函数开始时清空，避免重复运行或函数内重名串值。原始 IR 不被修改。

### R4：重复使用分配器时，空输入带回了上一轮指令

#### 发生了什么

寄存器分配器负责给指令中的临时变量安排实际寄存器。新增的 `allocate_result()` 接口会返回安排后的指令、变量与寄存器的对应表，以及需要的栈空间。

修复前，如果重复使用同一个分配器，第一次传入一条指令，第二次传入空列表，第二次的结果仍包含第一条指令。可以理解为上一轮的结果没有清干净。

```python
a = LinearScanAllocator()
a.allocate_result([MI(O.LI, P.vreg("v"), P.immediate(7))])
r = a.allocate_result([])
```

这里第一轮的指令是“把数字 7 放入寄存器”。第二轮没有指令，应该返回空结果，实际却如下：

| 第二轮返回的内容 | 应该是什么 | 修复前实际是什么 |
|---|---|---|
| 指令列表 `r.instructions` | 空列表 | 上一轮的 `[li %t0 7]` |
| 寄存器对应表 `r.register_map` | 空字典 | 空字典 |
| 栈上保存临时值的空间 `r.spill_bytes` | 0 字节 | 0 字节 |

结果中的指令来自上一轮，配套信息却来自当前这轮。后续代码拿到这个结果，就无法把指令和说明对应起来。

#### 为什么会出错

代码遇到空输入时直接返回了，但清空已保存指令列表的语句写在后面，没有执行。寄存器表和栈布局已经在分配阶段重置，只有指令列表留下来了。

相关位置：[regalloc_linear.py](../../../scratchv/backend/regalloc_linear.py#L275) 新增的 `allocate_result()`；[regalloc_rewrite.py](../../../scratchv/backend/regalloc_rewrite.py#L22) 第 22 行提前返回，而指令列表到第 103 行才重置。

#### 影响和课题关系

直接调用这个接口、并重复使用同一个分配器时，会收到旧指令。CompilerDriver 当前每次编译都会新建分配器，所以普通命令行编译通常不会遇到这一情况。

原始课题没有单独要求“分配器对象复用”这个功能，但我们为保留浮点类型信息新增了这个返回结果的接口。它返回的内容必须属于当前调用，因此这是新增代码的正确性问题，属于本次修复范围。

#### 我们怎么修复

在 [regalloc_rewrite.py](../../../scratchv/backend/regalloc_rewrite.py) 的 `rewrite_with_spills()` 一开始就创建新的指令列表，然后才判断输入是否为空。`allocate_result()` 和返回汇编字符串的 `emit()` 都经过这里，两种调用方式都得到修复。

这里必须创建新列表：如果对原列表调用 `clear()`，调用者之前拿到的结果也会跟着被清空。现在每轮使用自己的列表，旧结果保留原内容；空输入得到空指令、空寄存器表、空 spill 槽和零字节空间，即 `AllocationResult([], {}, {}, 0)`。

### R5：ONNX Min/Max 把 NaN 算成了正常数字（2026-10-13 复审）

#### 发生了什么

合法的 ONNX 标量模型计算 `Min(NaN, 2.0)` 或 `Max(NaN, 2.0)`，官方参考实现和 ONNX Runtime 返回 NaN，我们编译后的程序却返回 `2.0`。交换输入顺序也会出错。NaN 是浮点数允许存在的特殊值，表示没有得到有效数值；模型含有 NaN 不等于模型非法。

#### 为什么会出错，和课题有什么关系

[ONNX 前端](../../../scratchv/frontend/onnx_parser.py) 把 Min/Max 转成普通 IR min/max，[指令选择器](../../../scratchv/backend/inst_select_ext.py) 随后直接生成 RISC-V `fmin/fmax`。两边对普通数字的结果一致，但 NaN 规则不同：ONNX 官方参考实现使用 `numpy.minimum/maximum`，有一个 NaN 就返回 NaN；RISC-V 在只有一个 NaN 时选择另一个数字。指令合法、程序也能执行，却改变了原模型的结果。[ONNX Min 参考实现](https://raw.githubusercontent.com/onnx/onnx/v1.23.0/onnx/reference/ops/op_min.py)、[Max 参考实现](https://raw.githubusercontent.com/onnx/onnx/v1.23.0/onnx/reference/ops/op_max.py)、[RISC-V 浮点规范](https://raw.githubusercontent.com/riscv/riscv-isa-manual/main/src/unpriv/f-st-ext.adoc)

这属于课题新增 ONNX Min/Max 支持的正确性问题，优先级 P2。已在 f32/f64、三种分配器和多个优化配置下复现。普通 ONNX Min/Max 测试没有覆盖 NaN；另有 60 个常量编码测试虽然用了 NaN，却把选择正常数字当成了预期结果。用于核对 RISC-V 的 `minimum_number/maximum_number` 也会选择正常数字，不能作为 ONNX NaN 行为的独立对照。

#### 我们怎么修复

- [IRBuilder](../../../scratchv/ir/builder.py) 的 Min/Max 增加 `propagate_nan` 选项。ONNX 前端对每一步浮点 Min/Max 归约打开它，明确保留“输入含 NaN，结果也为 NaN”的要求；整数运算和 DSL 保持原来的规则。
- 后端先执行 `fmin/fmax`，再通过两个输入与自身的浮点相等比较检查 NaN。输入都是正常数字时直接保留结果；含 NaN 时才执行浮点加法，得到规范化的 quiet NaN。不能无条件做这次加法：两个大数相加可能溢出，正负无穷大相加会引入 invalid，而原来的 Min/Max 不应产生这些额外异常。
- [IRTraceExecutor](../../../scratchv/simulator/rv32_emulator.py) 同样读取这项 IR 标记，含 NaN 时返回 NaN。非 NaN 输入继续按既有 RISC-V 符号零规则处理，避免结果核对工具和实际程序不一致。本次修复针对 NaN 传播，不把符号零测试当作完整 ONNX 浮点语义一致的证明。
- 新增 [test_topic28_onnx_nan.py](../../../tests/test_topic28_onnx_nan.py)。三个既有常量编码测试文件中的 NaN 预期改为 NaN，并增加官方参考实现对照；原始编码、直接返回时的位模式、ABI 和 qNaN/sNaN 异常标志检查都保留，没有把失败测试改成跳过。

## 3. 为什么支持 f64 需要同时修改多个模块

旧代码已经有 `DataType.FLOAT64` 和部分双精度指令，但一个 f64 输入经过整个编译过程时，仍可能在中途被当成 f32、被安排到整数寄存器，或只保存了 4 字节。**要完成课题，需要让双精度值从输入到运行结果一直被正确处理。** 这就是为什么前端、类型、优化器、寄存器分配和输出代码都需要一起检查。

```mermaid
flowchart LR
    A[读取输入中的类型和常量] --> B[运算结果保留正确类型]
    B --> C[优化保持计算结果和约定的浮点行为]
    C --> D[选择对应类型的机器指令]
    D --> E[安排正确类别的寄存器并保留位宽]
    E --> F[寄存器不够时保存完整的4或8字节]
    F --> G[为每个函数安排栈空间和调用规则]
    G --> H[生成合法汇编并实际运行检查]
```

每一步漏掉，都可能导致具体错误：

| 如果撤掉的改动 | 直接后果 |
|---|---|
| 保留运算结果的类型 | 两个 f64 相加，结果却被标成 f32，后续按错误精度处理 |
| 保留常量原始编码，并用合法指令读取 | 负零或 NaN 的编码改变，或生成工具不认识的 `li.d` 指令 |
| 区分整数寄存器和浮点寄存器 | 浮点值被放到整数寄存器，或比较得到的布尔值被放到浮点寄存器 |
| 按类型保存栈上的临时值 | 8 字节的 f64 只保存 4 字节，丢失一半数据 |
| 统一安排函数的栈空间和调用规则 | 两份数据使用重叠空间，或函数返回时没有恢复栈和寄存器 |
| 保持浮点优化的正确性 | 优化前后得到不同的符号零、舍入结果或浮点异常标志 |
| 检查是否支持输入的类型和形状 | 不支持的输入被错误处理，编译器还报告成功 |

f32 和 f64 使用同一组浮点寄存器（FPR），通过位宽区分；地址仍放在整数寄存器（GPR）中。加载、保存和运算需要选择对应精度的指令。f32 放入更宽的浮点寄存器时，也要遵守处理器规定的表示方式。[RISC-V F](https://raw.githubusercontent.com/riscv/riscv-isa-manual/main/src/unpriv/f-st-ext.adoc)、[RISC-V D](https://raw.githubusercontent.com/riscv/riscv-isa-manual/main/src/unpriv/d-st-ext.adoc)

后面的逐文件评估使用四个标签：

| 标记 | 意义 |
|---|---|
| **核心必需** | 课题直接要求的功能，例如新增算子和 f64 运算 |
| **集成必需** | 让这些功能在完整编译过程中正确工作所需的配套修改，例如保留类型、安排栈空间 |
| **合同必需** | 我们在设计中额外承诺了某种行为，例如保留 NaN 原始编码；保留这个承诺，就需要相应实现 |
| **可选配套** | 方便使用或维护的工具，例如统计和汇编美化 |

这些标签判断的是需要实现什么能力。具体代码可以换一种写法，下面也列出了可替代或精简的部分。

#### 必须保留的语义例子

`onnx_bits.py` 是最值得单独划定维护边界的扩展：它读取源存储，不负责 ONNX 类型推导，也不是替代官方 protobuf parser。现有代码只处理 Model→Graph→initializer 路径并按 descriptor 取字段编号，这种限制合理。重复字段、unknown groups 等测试有依据，但不是每个编码变体都需要再乘上所有分配器和优化级别。

#### 指令选择为什么需要替换，而不是在旧代码旁追加

旧整数 min 使用 `slt` 的 0/1 直接与差值做 AND，0/1 不是全位掩码。例如 `min(7,2)` 的旧序列得到 7。新实现先计算 `mask=0-cond`，得到 0 或 `0xffffffff`，再按位选择完整的输入。这是正确性修复，不能因为新序列有 5 条指令就认定它是多余改动。max 可以继续用正确的伪指令展开、分支或当前掩码序列；**必须正确选择整值，当前无分支方案不是唯一必要方案**。

旧 IR 中的整数常量可以直接变成 MachineOperand immediate，而 `add/sub/mul/div` 等需要寄存器源。`mul rd,7,3` 不能作为正常 RV32 汇编交给 Clang。新增统一 materialize helper 是真实硬件路径的必要修复；合法性修复增加静态指令数不等于性能回退。

浮点比较的目的寄存器是 GPR 布尔值，浮点数据本身仍在 FPR。`!=` 使用 feq 结果为零分支；`>`/`>=` 交换源后使用 flt/fle。无需发明不存在的浮点 branch 指令。这些映射合理。

`li.d` 被常量池 `.word/.quad + la + flw/fld` 代替，确保生成标准工具能处理的编码。保留 `-0.0` 和 NaN 时应按 `(dtype,bits)` 去重，不能按 Python 数值相等去重。对 f32 也可以用整数位物化加 `fmv.w.x` 等合法方案；使用常量池是统一、可靠的实现选择，而非唯一实现。

显式 `rne` 使目标运算不依赖调用者当前 frm；如果数值合同只写“遵循调用者舍入模式”，这段可以不同。但本分支明确承诺固定 RNE，因此舍入属性从 selector 到 rewrite/emitter 全程保留是**合同内必需**。[RISC-V F 舍入与状态](https://raw.githubusercontent.com/riscv/riscv-isa-manual/main/src/unpriv/f-st-ext.adoc)

以下例子解释为什么这些改动不能视为与 topic28 无关的“顺手重构”：

1. **i32 中间溢出。**`(2147483647+1)/2` 必须先得到 `-2147483648`，再除以 2；无界 Python 整数一路折叠会得到相反符号。仅在最后包一层 i32 无法修复中间步骤。
2. **f32 逐步舍入。**先 `16777216.0+1.0`，再减 `16777216.0`，f32 路径结果为 0；以宿主双精度连续折叠则可变成 1。
3. **IEEE 非整数恒等式。**`Inf*0` 不能改成 0；`x+0` 也不能一概消去符号零和 signaling NaN 的行为。
4. **未使用不等于无效果。**未使用的 `sqrt(-1)` 仍可设置 NV；在零次循环之外提前执行则增加了原程序没有的异常标志。此处可观察性来自本分支明确选择的 fflags 合同。[RISC-V F 浮点状态](https://raw.githubusercontent.com/riscv/riscv-isa-manual/main/src/unpriv/f-st-ext.adoc)
5. **旧融合没有合法消费者。**旧 pass 把 `a*b+acc` 变成三源 `ADD [acc,a,b]`，而 selector 消费前两源。对 `2*3+4`，这甚至会算成 `4+2`；继续保留该转换没有正确性依据。

保守程度仍可优化：FNEG/FABS 等符号操作通常不设置 fflags，未用结果无需全部视为 effectful；某些静态可证明的浮点折叠也可能安全。但这些属于以后精化副作用模型，**现在用保守规则保证合同合理，全部禁用也不是理论上唯一必要的实现**。

#### 可以更小但不能失去的工程边界

ABI 通过 `[regalloc:*]` 注释及正则重写字节偏移，是沿用旧管线的实现成本选择；有测试保护时可以作为当前实现，但需要把这些标记当结构协议保护。后续应让 StackSlotRef 在最终布局前一直保留结构化身份。**不能只把注释删掉当美化，否则当前生产布局会失效。**

`_record_allocation_stats` 重新调用 emitter 统计站点，与核心代码生成无关，可拆成独立观测改动。这些数值是 selected/allocated 阶段统计，不能把它们当最终 ABI/汇编 pass 后的完整动态成本。

单标量参数、三组目标、非张量形状、硬件 sqrt、固定 RNE，以及不启用 DAG/LLVM 的 extended selector 都是清晰的范围选择。若用户要求这些边界之外的能力，需要继续实现；当前不应据此要求把整个 RISC-V 后端一次扩展为通用框架。

## 8. 当前修复状态和后续建议

五个已确认错误都已修复：R1 对 LLVM 暂不支持的整数操作明确报错；R2 区分不同函数的同名变量；R3 按原始编码读取浮点常量；R4 每轮重新建立指令列表，空输入不再返回旧内容；R5 保留 ONNX 浮点 Min/Max 的 NaN 传播。每项都先补充测试，再修复代码，前后结果见第 2 节。最新全量回归为 **3826 通过、0 失败、0 跳过**。

后续仍建议补充文档中的接口说明：旧的 ExtendedInstructionSelector 构造参数如何迁移，设计草案中的接口与实际代码如何对应，以及当前点积示例只展示标量乘加、没有证明通用张量点积已支持。

本课题需要保留的能力是：**从输入到结果保持正确类型，选择真实的单/双精度指令，使用正确的寄存器，完整保存 8 字节的 f64，生成合法汇编，正确处理函数调用，并保证优化不改变约定的结果。** 对非常规 protobuf 编码的支持、统计和美化工具、部分更严格的浮点保证，可以单独划分维护范围。调整范围时，应同步说明和测试，让读者知道实际支持到哪里。
