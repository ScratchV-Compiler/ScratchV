## Spec

### R7，P1：LLVM 接受新常量输入，却输出无效文件或错误数值（已在本地修复）

#### 发生了什么

以下三个程序都只有一条常量定义，然后 `return a`。使用 `CompilerConfig(backend="llvm", optimize_level=...)`，不启用 extended selector。

| 常量定义 | 修复前实际结果 | 修复后实际结果 |
|---|---|---|
| `a = const(1.2,dtype:f32)` | `success=True`、空错误列表，LLVM 解析失败 | 解析、验证通过，返回正确 f32 编码 `0x3f99999a` |
| `a = const(1.0000000000000002,dtype:f64)` | LLVM 验证通过，实际返回 `1.0` | 返回 `1.0000000000000002`，编码为 `0x3ff0000000000001` |
| `a = const(-0.0,dtype:f64)` | LLVM 验证通过，实际返回正零 | 返回负零，编码为 `0x8000000000000000` |

三项在 `none/basic/all` 下都独立复现，共 9 个场景。

第一项生成 `%v_1_1 = fadd float 1.200000e+00, 0.0`，当前 llvmlite/LLVM 报 `floating point constant invalid for type`。第二项应有位模式 `0x3ff0000000000001`，实际为 `0x3ff0000000000000`。第三项应有 `0x8000000000000000`，实际为 `0x0000000000000000`。

#### 为什么出错，为什么与本次变更有关

[DSL 前端](../../../scratchv/frontend/dsl_parser.py#L170)向共享编译入口开放了 typed const，[LLVM 类型检查](../../../scratchv/backend/llvm_codegen.py#L31)也明确允许 f32/f64。但旧的[常量格式化](../../../scratchv/backend/llvm_codegen.py#L625)使用默认 `:e`，只保留七位有效数字，不能精确表达这些浮点值；[常量加载](../../../scratchv/backend/llvm_codegen.py#L303)还用 `fadd 常量, +0.0` 构造常量，导致负零变为正零。

原始要求第 11–12 行要求添加双精度支持、区分 f32/f64。这里不是要求课题实现 LLVM 的全部功能，而是共享前端开放新输入后，接收它的后端必须正确处理或明确拒绝。精确导出的基线 `f3af99d` 对同一 typed const 语法明确返回失败；HEAD 变成接受输入后给出错误产物。不能据此声称基线其他浮点入口原来完全正确。

#### 审查时的修复建议

按目标精度和准确位模式输出 LLVM 常量，避免用浮点加零来复制常量；暂未支持的情况应返回失败。覆盖 f32 普通小数、f64 最低有效位、正负零及特殊值。测试先解析/验证，再实际执行并核对位模式：仅能通过 LLVM 验证，仍可能返回错误数值。

三项都经过 LLVM 解析/验证；解析成功的两个 f64 场景进一步通过原生 MCJIT 核对实际返回值。为在本机执行，只设置了模块的本机目标三元组和数据布局，没有修改生成的函数指令。主审也独立复核了相同结果。

#### 我们怎么修复（2026-10-14）

- [llvm_codegen.py](../../../scratchv/backend/llvm_codegen.py) 按 f32/f64 编码常量，以 LLVM `bitcast` 直接表示原始位模式。加载常量也改用 `bitcast`，不再用浮点加零，因此普通小数、最低有效位和负零都能保留。
- 常量有明确 `bit_pattern` 时优先读取编码；LOAD_CONST 的指令属性和结果 Value 都可以提供编码，两者冲突或编码无效时明确拒绝。ONNX initializer 和直接用作操作数的常量使用同一条精确表示路径。
- 补测发现，旧的 `basic/all` 还会先用宿主精度折叠 f32 运算：`f32(16777217)-f32(16777216)` 应为 0，旧折叠却得到 1。[CompilerDriver](../../../scratchv/compiler.py) 的 LLVM 路径现在启用现有浮点语义保护，预设级别和显式 pass 均适用，让 LLVM 执行这些按声明精度计算的运算。浮点折叠等变换因此更保守；本次没有测量或声称性能提升。
- 新增 [test_llvm_scalar_constants.py](../../../tests/test_llvm_scalar_constants.py)，按测试类组织。保留 R1 的整数拒绝检查；本次没有修改 R6 的 ONNX 符号零行为。

### R6，P2：ONNX Min/Max 的正负零处理，让后续结果符号相反

#### 发生了什么

正零和负零相比较时数值相等，但它们参与后续浮点除法，结果符号不同。两个通过 ONNX checker 的合法标量模型得到：

| 模型计算 | ONNX 官方参考实现和 ONNX Runtime | 编译后实际执行 |
|---|---|---|
| `1.0 / Min(-0.0, +0.0)` | 正无穷大 | 负无穷大 |
| `1.0 / Max(+0.0, -0.0)` | 负无穷大 | 正无穷大 |

覆盖 Min/Max × f32/f64 × naive/greedy/linear × none/basic/all，**36 个真实 ELF/QEMU 场景都出现差异**。

#### 为什么出错，现有测试为什么通过

原始要求第 5 行要求增加 ONNX 算子支持，第 31 行包含 Min/Max。[浮点选择器](../../../scratchv/backend/inst_select_ext.py#L308)在非 NaN 情况仍直接使用 RISC-V `fmin/fmax`。它们把负零排在正零前面；本次测试中，两个 ONNX 实现都选择了相等输入中的第二个。

README 第 56 行已声明沿用目标的符号零约定，[现有符号零测试](../../../tests/test_topic28_onnx_nan.py#L206)也直接检查这个目标预期。因此测试通过，但它不能证明源 ONNX 模型的结果得到保留。R5 的 NaN 修复仍有效，这里报告的是另外一种输入。

准确限定：公开的 [ONNX Min 算子说明](https://onnx.ai/onnx/operators/onnx__Min.html)没有明文规定正负零相等时选哪一个。本项报告的是与[官方 Min 参考实现](https://raw.githubusercontent.com/onnx/onnx/v1.23.0/onnx/reference/ops/op_min.py)、[Max 参考实现](https://raw.githubusercontent.com/onnx/onnx/v1.23.0/onnx/reference/ops/op_max.py)及 ONNX Runtime 都不一致、并能改变后续结果的兼容性问题，不把它描述为违反某条明确写出的符号零规范。

#### 建议修复和补测

分别保留 ONNX 与 DSL 的浮点规则。在 ONNX 路径中处理相等的正负零选择，并补测两种输入顺序、多个输入和 Min/Max 后接 Div 的模型。预期应来自独立 ONNX 实现；DSL 可继续保持已经约定的 RISC-V 行为。

六项原始要求及 W9/W10 均有对应实现，本轴没有确认其他独立缺项或越界工作。
